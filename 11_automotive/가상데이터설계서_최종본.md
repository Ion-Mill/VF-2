## 1. 왜 가상 데이터인가

| 필요한 데이터 | 공개된 실제 데이터 | 상태 |
|---|---|---|
| 설비 상태 + 알람 + 생산 로트 + 정비 + 검사 + 재고가 **한 라인에서 함께** 있는 기록 | 없음 | 찾지 못함 (탐색 보고서 7장) |
| Haas VF-2 실제 운영 기록 | 없음 | 찾지 못함 |
| 조각 자료 | NIST 설비 상태 기록, 4TU 생산 기록, Haas 원시 데이터 표본, 벽돌 라인 정지 기록, Haas 공구 수명 실험 | **있음 — 모양을 빌려 온다** |

그래서 **한 라인의 운영 기록은 가상으로 만들되, 숫자의 크기와 모양은 실제 조각 자료에서 가져온다.** 알람 번호, 알람 설명, 정비 항목처럼 문서에 있는 것은 실제 값만 쓴다.

## 2. 여섯 가지 원칙

| # | 원칙 | 구체적으로 |
|---|---|---|
| 1 | **실제 번호만 쓴다** | 알람 번호·이름·설명은 Haas 알람 목록에 있는 것만. 정비 항목은 Haas 정비 일정에 있는 것만 |
| 2 | **크기는 실제 자료를 따른다** | 상태 변화 횟수, 정지 시간, 로트 수량, 불량률을 3장의 실제 값 범위에 맞춘다 |
| 3 | **서로 맞아야 한다** | 알람 정지 시간 = 상태 기록의 DOWN 시간 = 작업기록서의 수리 시간. 로트 완료 수량 = 마지막 공정 양품 합. 재고 감소 = 사용 기록 합. 완제품 재고 = 합격 입고 합 − 출하 합 (5.20) |
| 4 | **가상임을 표시한다** | 모든 테이블에 `is_synthetic = true`. 화면의 가상 값에는 [가상] 꼬리표, 비서 답에는 "가상" (화면 구석의 "가상 운영 데이터" 표시는 2026-10-07 팀 UI 검토로 뺌) |
| 5 | **다시 만들 수 있어야 한다** | 고정 난수 씨앗(seed)과 설정 파일. 같은 설정이면 같은 데이터 |
| 6 | **빌려 온 값은 출처를 남긴다** | 다른 회사·설비 값은 [참고]와 출처를 붙이고, **정상 범위만** 빌린다. 알람 기준값은 만들지 않는다. 압력은 psi와 bar를 함께 적는다 (1 bar ≈ 14.5 psi) |

## 4. 생성기 전체 구조

```
설정 파일 (config.json)
   │  기간, 설비, 교대, 제품, 교대 목표, 확률 값, seed
   ▼
① 기준 정보       설비(외형 크기·배치 좌표), 공장 배치·배치 물체·설비 부품 도형, 제품(BRK-A100),
   │               공구, 재고 품목(13개, 관리 역할), 출하처, 사용자, 정지 사유, 예방 정비 항목
   ▼
② 생산 계획       원자재 로트 입고, 날짜별 작업지시(수량, 납기 = 시작 교대로 정함, 5.5) → OP-10 투입 때 교대별 생산 로트로 나눔
   ▼
③ 시간 흐름       1분 단위로 공정·설비마다 상태를 바꾸고 부품을 다음 공정으로 넘김
   │   - 가공 → 다음 부품 / 로트 교체 셋업 / 공구 교체
   │   - 알람이 확률적으로 생김 → 정지 → (정비 필요하면) 작업지시 → 복구
   │   - 예방 정비 기한이 되면 계획 정비
   ▼
④ 파생 기록       공정 실적, 재공, 병목 기록, 검사 계획(발췌·전수)과 결과(측정 결과 파일 가져오기 기록 포함),
   │               공구 사용량(구멍 수·이송 시간), 재고 입출고(완제품 합격 입고 포함), 반복 알람 1·2단계
   ▼
⑤ 문서 기록       작업지시서(계기: 정지 등급 알람 / 반복 알람 2단계), 작업기록서, 출하 기록(납기일),
   │               교대 보고서(17:00·05:00)·일일 보고서(06:00), 수정 이력
   ▼
⑥ 점검           9장 기준으로 자동 점검 → 통과하면 DB에 넣기
```

| 모드 | 쓰임 | 내용 |
|---|---|---|
| 과거 기록 모드 | 30일치 차트·지표·이력·문서 | 2026-09-01 ~ 09-30, 한 번에 생성 |
| 실시간 모드 | 시연 때 화면이 움직이게 | 몇 초마다 상태·센서·실적을 보냄. 시간을 빠르게 돌릴 수 있음 (예: 1초 = 1분) |
| 사건 넣기 | 시연 시나리오 | 버튼 하나로 7장의 정해진 사건을 발생 |

실시간 메시지는 Haas MTConnect 항목 이름(Execution, ControllerMode, EmergencyStop, Program, PartCount 등)을 따른다.

- 측정값(`inspection_result`)은 **측정한 부품만** 만든다. 발췌 로트는 측정 부품 수가 적다.
- 로트 판정: 측정한 부품 중 1개라도 불합격이면 그 로트를 "보류 검토"로 표시하고 전수로 바꾼다.
- Cpk는 측정한 값으로 계산한다.
- **측정 전 온도 맞춤** (DOC-06 §6.1, 세척 50 ℃ 기준): 측정할 부품은 "온도 맞춤 선반"에 두고 CMM 부품 온도 보정으로 잰다. 초품은 송풍 냉각 약 17분(셋업 시간 안), 발췌 측정 부품은 90분 이상, 보정을 못 쓰면 140분 이상 [가상, 계산 근거는 참고]. 게이지·육안 부품은 기다리지 않는다.
  - 생성기 규칙: 온도 맞춤 선반의 부품은 **OP-40→50 재공 한도에 세지 않는다.** 측정값(`inspection_result`)의 측정 시각 = 세척 완료 + 대기 시간 이후. **로트 판정은 그 로트의 측정 부품을 모두 잰 뒤**에 기록한다 (그 전 로트 상태는 "판정 대기").
  - 로트가 합격 판정되면 그 시각에 완제품 합격 입고 거래가 생긴다 (5.14).

### 5.18 병목 상황 (고장이 아닌 원인)

설비가 멈추지 않아도 한 공정이 느려지면 병목이 생긴다. 과거 30일 데이터에 **원인 4가지를 모두** 넣는다. 모든 값은 [가상]이다.

| # | 원인 | 만드는 규칙 | 30일 빈도 | 병목 위치 |
|---|---|---|---|---|
| ① | 사이클 시간 증가 | 공구 수명 80%를 넘으면 해당 VF-2의 사이클 시간 7.0 → 8.0~8.5분 (공구 교체하면 회복) | 주 1~2회, 2~4시간 | OP-30이 더 심해짐 (라인 3.5 → 약 3.8분/개) |
| ② | 설비 1대만 가동 | VF2-01 또는 02의 매월 예방 정비(60~90분), 긴 셋업, 반복 알람 2단계 원인 점검(5.8 사례 ②, 1회) 동안 OP-30을 1대로 운영 | 4~6회 (원인 점검 1회 포함) | OP-30 (7.0분/개, 속도 절반) |
| ③ | 검사 강화 | 의심 로트가 보류되면 그 로트와 다음 1~2개 로트는 **발췌 → 전수 + 항목 확대** → OP-50 평균 약 0.9 → 5.0분/개 | 2~3회 (보류 로트와 같은 수) | **OP-50으로 이동** (5.0분 > 라인 3.5분) |
| ④ | 묶음 대기 | OP-40은 30개가 모여야 세척 시작. OP-30→40 한도는 60개라 평소에는 막힘이 생기지 않음 | 매일 (작은 규모) | OP-30→40 사이에 잠깐 쌓임 (병목 판단에서는 제외) |

**계산 예 (원인 ②, 90분)**

| 항목 | 값 |
|---|---|
| OP-20 내보내는 속도 | 1개 / 3.5분 |
| OP-30 처리 속도 (1대) | 1개 / 7.0분 |
| OP-20→30 재공 증가 | 1분에 약 0.14개 → 90분에 약 13개 (18개에서 시작하면 한도 30개 도달 → OP-20 BLOCKED) |
| 속도 손실 | 계획 약 26개 − 실제 약 13개 = **약 13개** |

**병목 판단 규칙** (생성기와 플랫폼이 같은 규칙을 씀, DOC-07에 적음)

- 최근 30분 동안 **바로 앞 재공이 늘고**, 앞 공정이 BLOCKED이거나 뒤 공정이 IDLE(앞 공정 대기)인 공정을 병목으로 본다.
- 조건에 맞는 공정이 여럿이면 앞 재공이 가장 많은 공정을 고른다. 아무 공정도 맞지 않으면 기준 병목(OP-30)으로 표시한다.
- 병목 공정이 바뀌면 `bottleneck_log`에 기록한다: 시각, 이전 병목, 새 병목, 원인 번호(①~④ 또는 고장).
- 병목 발생·이동 알림에는 **DOC-07 §7.5 병목 원인별 조치**의 해당 원인 줄이 관련 정보로 붙는다 (2026-10-06 결정). 원인 번호가 있어야 줄을 고를 수 있으므로 모든 병목 기록에 원인 번호를 남긴다. 조치는 사람(SUP)이 하고, 고른 조치는 교대 보고서 병목 칸에 원인 번호와 함께 남는다 [제안].

### 5.19 다시 보기(PRD-06)용 기록

**새로 만드는 데이터는 없다.** 이미 있는 기록을 시각 순서로 다시 그린다. 다만 다시 볼 수 있을 만큼 기록 간격을 정해 둔다.

| 기록 | 간격 | 비고 |
|---|---|---|
| 설비 상태 (equipment_state_log) | 바뀔 때마다 | 그대로 |
| 재공 (wip_log) | 5분 | 시연 사건 전후 30분은 1분 |

- 데이터 보관 기간(NFR-DATA-13, DOC-07 §11)은 1초 센서 구간이 가장 짧은 90일이다. 가상 데이터는 30일이라 **시연에서 지워지는 기록은 없다** (11장).

**출하 로트 줄 (shipment_line)**

| 칸 | 규칙 |
|---|---|
| 출하 번호 | 머리 연결 |
| 생산 로트 | 합격(해제 포함) 로트만 |
| 수량 | 이 로트에서 내보낸 수량 (로트 남은 수량 이하). 가상 데이터는 로트를 쪼개지 않으므로 = 로트 남은 수량 전부 |
| 로트 합격 시각 | FIFO 확인용 (로트 기록에서 가져옴) |

**가상 출하 생성 규칙** (완제품 조사 1.7)

| 번호 | 규칙 | 구분 |
|---|---|---|
| G1 | 생산일 = 그날 주간 + 그날 밤 야간 (5.2). 작업지시 투입일 = OP-10 첫 투입의 생산일 | [가상] |
| G2 | 납기 = 주간 교대 시작 작업지시는 생산일 + 1일, 야간 교대 시작은 + 2일. 일요일이면 월요일 (5.5) | [가상] |
| G3 | 출하는 **납기일 주간 교대 중 하루 1번, 14:00** | [가상] (시각 숫자는 팀이 정한 값. 출하 확인자 SUP가 근무 중이고, 야간 로트 판정이 오전에 끝난 뒤) |
| G4 | 출하 수량 = 그날 납기인 작업지시들의 합격 로트 수량 전부. 로트는 합격 시각 순(FIFO)으로 줄에 넣는다. **로트를 쪼개지 않는다** | [제안] |
| G5 | 출하 시각에 그 작업지시 로트가 보류·판정 대기이면 그 로트는 빼고 나머지만 출하한다 (**부분 출하**, 비고에 사유). 뺀 로트는 해제·합격된 뒤 다음 출하에 넣고 "납기 지남"을 표시 → 30일 중 늦은 출하 1~2건 (5.5 보류 2~3건에서 자연히 생김) | [제안] |

| G7 | 출하처 1곳 (`CUST-01`), 출하 확인자 = 그날 주간 SUP | [가상] |
| G8 | 기초 재고 = 9월 1일 0개. 9월 1일은 출하 없음, **9월 2일 첫 출하**. 납기가 10월인 로트는 9월 말에 재고(또는 판정 대기)로 남는다 | [가상] |

**요일별 출하량 예** (교대 실적을 평균 90개로 둔 계산. 실제 값은 생성 뒤 확인)

|---|---|---|
| 월 | 금 야간(+2 = 일 → 월), 토 주간(+1 = 일 → 월), 토 야간(+2 = 월) | 약 270개 (3교대분) |
| 화 | 월 주간(+1) | 약 90개 |
| 수~토 | 전날 주간(+1) + 그 전날 야간(+2) | 약 180개 |

**30일 규모** [계산]

| 항목 | 값 |
|---|---|
| 출하 건수 | **25건** (`SHP-2609-001` ~ `025`) — 9/2 ~ 9/30 근무일마다 1건. 근무일마다 납기가 되는 작업지시가 있다 (위 표) |
| 출하 로트 줄 | 생산 로트(130~160개) 중 9월 말까지 출하된 로트 수만큼. 늦은 출하 로트도 1줄 |
| 출하 수량 합 | 30일 합격 합 − 9월 말 남은 재고 |
| 9월 말에 남는 것 | 납기가 10월인 9/29 야간·9/30 주간·9/30 야간 시작 작업지시의 로트 (약 3교대분). 판정이 끝난 로트는 완제품 재고, 끝나지 않은 로트는 "판정 대기" |
| 완제품 재고 흐름 | 대략 하루~이틀 생산분(약 90~360개)으로 오르내림. 토요일 밤~월요일 출하 전이 가장 많음 [계산 예상 — 생성 뒤 점검으로 확인] |

- 이미 출하한 로트는 나중에 보류할 수 없다(공장 밖). 로트 추적(PRD-05)에는 "출하됨 — SHP-…"과 출하처를 보여 준다. 고객 통보·회수는 범위 밖 [제안].
- 로트 추적 사슬: 원자재 로트 → 생산 로트 → 검사 → 출하.
- 생성 뒤 점검 6줄은 9장에 있다.

## 10. 파일 구조와 재현 방법

```
simulator/
  config.json          기간, 설비, 교대, 제품, 교대 목표, 확률 값, seed
  masters/             설비(외형 크기·배치 좌표·참고 모델), 제품, 공구(사용량 단위·한도),
                       재고 품목(13개, 관리 역할), 출하처, 사용자, 정지 사유, 알람 등급(다른 공정 포함), 검사 방식 (CSV)
    plant_layout.csv          공장 배치 (1행: 가로·세로·천장, 원점·방향) — 5.1
    layout_object.csv         배치 물체 (봉재 랙, 투입 대, 재공 자리, 온도 맞춤 선반, 완성품 자리, 통로, 문) — 5.1
    equipment_part_shape.csv  설비 부품 도형 (설비, 부품, 상자/원기둥, 크기, 상대 위치) — 5.1
  generate.py          과거 기록 모드
  realtime.py          실시간 모드 + 사건 넣기 (+ CMM 결과 파일 예시 떨어뜨리기, 5.15)
  scenarios/           S1~S6 정의 (JSON)
  validate.py          9장 점검
  out/                 생성 결과 (CSV) → DB 적재 (출하·출하 로트 줄, 측정 결과 파일 가져오기 기록 포함)
```

- 같은 `config.json`과 `seed`면 같은 결과가 나와야 한다.
- 형식 (2026-10-06 결정): 설정 파일(`config.json` — 라인 구성·교대 시간·확률 값 등)과 시뮬레이터 사건 넣기(`scenarios/`)는 **JSON**으로 쓴다. 기준 정보와 생성 결과는 CSV로 만들어 **DB에 넣는다** (운영 데이터 저장은 JSON 파일이 아니라 DB). (v3까지는 YAML로 적었다)
- 생성 결과 CSV는 저장소에 올려도 된다. Haas·Siemens 원문과 번역본은 팀 비공개 저장소에만 둔다.

## 11. 한계와 심사 때 설명 방법

| 예상 질문 | 답변 방향 |
|---|---|
| "데이터가 가짜 아닌가요?" | 운영 기록은 가상이 맞다. 알람 번호·정비 항목·안전 절차는 실제 문서 근거이고, 숫자 크기는 실제 공개 기록(NIST, 4TU)에 맞췄다. 9장 기준으로 점검했다 |
| "센서 값은 어디서 왔나요?" | 다른 Haas 설비(선반)의 실제 원시 데이터에서 정상 범위만 빌렸다. 화면과 문서에 [참고]로 표시했다 |
| "손실 수량은 정확한가요?" | 정지 시간 ÷ 기준 사이클 시간으로 낸 **추정치**이고, 계산식을 DOC-07에 공개했다 |
| "실제 설비에 붙일 수 있나요?" | 메시지 항목 이름을 Haas MTConnect에 맞췄다. 실제 설비는 포트 8082나 Q 명령으로 같은 값을 받을 수 있다 |
| "공구 수명 예측이 정확한가요?" | 실제 Haas 실험 데이터로 학습했고 R² 약 0.55~0.65로 중간 수준이라, 화면은 사용량(구멍 수·이송 시간) 기준 알림이 기본이다 |
| "로트를 왜 교대마다 나누나요?" | 자동차 협력사 추적성 기준이 교대 변경·공정 재시작 때 로트 번호를 바꾸라고 한다 (Panasonic §6.3). 우리 라인은 교대 사이에 3시간 멈춘다 |
| "전수 검사를 안 하나요?" | 평소에는 발췌, 공정이 의심되면 전수다. 협력사 품질 기준(Nemak)과 샘플링 규격(MIL-STD-1916)의 전환 방식을 따랐다 |
| "알람 기준 온도는 어디서 왔나요?" | 만들지 않았다. Haas 문서에 없기 때문이다 |
| "3D 설비 크기는 진짜인가요?" | SAW-01·VF-2는 제조사 자료의 실제 크기, MIL-01·WSH-01·CMM-01은 비슷한 실제 모델의 크기를 빌린 [참고] 값이다. 배치 좌표와 공장 크기는 Haas 둘레 여유 914 mm 등 근거로 팀이 정한 [가상] 값이다 (5.1) |
| "완제품은 어디로 가나요?" | 합격 로트만 완제품 재고에 들어가고, 납기일 14:00에 가상 고객사 `CUST-01`로 출하한다. 주문·ERP는 범위 밖이라 납기는 투입 교대로 정했다 (5.20) |
| "측정값은 사람이 치나요?" | 아니다. 측정기가 쓴 결과 파일을 플랫폼이 읽는다. 게이지·외관만 태블릿 버튼이다 (5.15) |

## 13. 가상 사내 문서 제작 기준

### 13.1 무엇을 만드나

흩어진 실제 문서(영어·한국어)에서 **이 프로젝트 구현에 필요한 내용만** 뽑아, 한국어로 다시 만든 사내 문서 7종(DOC-01~07)과 용어집(00_용어집). 전체를 "가상 사내 문서 세트"라고 부른다. AI 비서는 **이 세트(DOC-01~07 + 용어집)만** 검색한다. 원문은 검색하지 않는다.

- **비서·화면은 원문 출처를 표시하지 않는다** (2026-10-06 결정). 답·지침카드·문서 초안·화면의 출처는 사내 문서 이름 + 문서 번호 + §절만 쓴다 (예: "고장 대응 매뉴얼 DOC-03 §2.1", "용어집 §4"). 쪽 번호는 쓰지 않는다.
- 사내 문서 **본문 안**의 항목별 출처([실제]/[참고]/[가상])와 원문 대응표는 그대로 둔다. 사람이 근거를 추적하는 용도이고, 비서는 인용하지 않는다.

### 13.3 서로 다를 때 무엇을 따르나 (우선순위)

```
① 법령  >  ② KOSHA  >  ③ 해당 설비·제어기 세대의 제조사 문서  >  ④ 공식 규격(ISO 등)  >  ⑤ 다른 회사 사례  >  ⑥ 팀 가정
```

| 상황 | 따르는 것 |
|---|---|
| 안전 절차가 서로 다름 | **더 엄격한 쪽.** 둘 다 지킬 수 있으면 둘 다 넣는다 (예: KOSHA 잠금·표지 + Haas 고전압 5분 대기) |
| 같은 알람에 문서가 여러 개 | NGC 문서 > 구형 문서. 최신 개정판 > 옛 판 |
| 품질 기준이 회사마다 다름 | 공식 규격 > 여러 협력사 문서에 공통인 값 > 한 회사 값 |
| 근거 문서가 없음 | 팀이 정하고 **[가상]** 으로 표시 |

### 13.5 번역 규칙

| 규칙 | 뜻 |
|---|---|
| **용어집 먼저** | 번역 시작 전에 용어집(약 50~100개)을 만든다. 예: Servo Amplifier → 서보 앰프, Lockout/Tagout → 잠금·표지, Way Lube → 축 윤활유. Haas 한국어 알람 목록의 용어를 우선 쓴다 |
| **쉬운 한국어** | 현장 작업자가 바로 읽을 수 있게 쓴다. 영어 이름은 처음 한 번만 괄호로 |
| **바꾸지 않는 것** | 안전 절차, 알람 설명, 숫자(전압, 시간, 압력, 토크)는 원문 뜻 그대로. 요약하거나 새로 쓰지 않는다 |
| **단위** | 원문 단위를 두고 국내 단위를 괄호로 함께 적는다. 예: 100 psi (약 6.9 bar), 1 inch (25.4 mm) |
| **방법** | LLM으로 번역 → 담당자가 원문과 대조해 검수 → 안전·알람 항목은 다른 팀원이 한 번 더 확인 |
| **원문 복사 금지** | 긴 문단을 그대로 옮기지 않고 필요한 내용만 정리한다. 단, 안전 절차 단계 제목(KOSHA 6.1~7.3)과 알람 이름은 원문 그대로 쓴다 |

| 항목 | 규칙 |
|---|---|
| 개정 | 내용을 고치면 개정 번호를 올리고, 바뀐 내용·사유를 수정 이력(AST-03)에 남긴다 |

- 절삭유 목표 농도 7.0% [실제]: SC538 제품 자료 2쪽 "일반절삭가공 (Moderate duty) 6.5% - 8.5%", "7% 이상에서 작동 시 최상의 탱크 수명 및 부식 방지 제공". 포장 20 L [실제: 같은 자료 3쪽].
- 주축 윤활유 [참고/실제]: 0.6 cc/시간은 다른 회사의 공기·오일 윤활 권장값이다 (Plant Services 2002, `docs/inventory/소모품_사용량/plantservices_2002_공기오일윤활_주축베어링_Mitchell.html`). Haas 자료에는 소비량이 없다. 오일 종류·128 oz는 RD0040 [실제]. 이 속도면 한 통이 약 7개월 가므로 9월 안에 안전 재고 아래로 내려가지 않는다.
- 그리스 [실제/가상]: 카트리지 14 oz(0.41 L)와 부품 번호 99-1686은 RD0040 [실제]. 1회 주입량은 Haas 자료에 없어 g으로 빼지 않고 카트리지 단위로 뺀다 [가상]. OP-40 텀블러도 같은 그리스(XHP 222)를 쓴다 [가상]: 진동 기계 베어링에는 EP 첨가 리튬 비누 그리스·주도 2급을 권한다 [참고: FAG TPI 197 인쇄 34쪽]. 1번 누름 1.5 cm³ [참고: SKF 1077600 H 그리스건 사양], 니플 2개·하루 2회 [가상]. 카트리지 1개가 약 68일 가므로 9월 한 달에는 카트리지 교체가 0~1번 생긴다 (DOC-04 4.5).
- 축 윤활유는 실제 소비 속도(한 통이 우리 라인에서 약 4~5개월)로는 9월 안에 안전 재고 아래로 내려가지 않는다. 시연 S2를 위해 **9월 말 "보충을 빠뜨림" 사건**을 따로 넣는다 (LUBE-SM-02 "한 통이 주 40시간 기준 약 10개월~1년").
- **원자재 입고 고침:** 주 2회 × 400개(800개)는 주 소비 1,080개(6일 × 180개)보다 적다 → **주 3회 × 약 360개**로 바꾼다.

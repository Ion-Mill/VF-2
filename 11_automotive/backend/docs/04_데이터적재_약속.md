# 04. 데이터 적재 약속 (생성기 → DB, 사내 문서 → DB, 측정기 → DB)

> 가상 데이터 생성기(`VF-2/11_automotive/생성기`)가 만든 CSV, 가상 사내 문서(`가상사내문서/`), OP-50 측정기(CMM) 결과 파일을 DB에 넣는 약속.
> 기준: **논리 ERD 11.1 "생성기 CSV를 DB에 넣을 때" (2026-10-14)**. 3장 표는 `tools/gen_load_contract.py`가 실제 DB와 생성기 CSV에서 만든다.

## 1. 생성기 CSV 약속 (논리 ERD 11.1)

| 항목 | 약속 |
|---|---|
| 파일 | 엔터티 1개 = CSV 1개, 이름 = `<테이블>.csv`. 기준 정보 `masters/` 22개 + 9월 `out/` 34개(센서 포함) + manifest. 10/1 리허설 `out_realtime/` 17개 |
| 머리 줄 | 논리 ERD 5장 속성 이름 (생성기는 5장 순서). 적재 도구는 **이름으로** 맞춘다 — CSV에만 있는 칸(아래 "넣지 않는 칸" 빼고)이나, DB 필수인데 CSV에 없는 칸이 있으면 아무것도 넣지 않고 멈춘다 (종료 코드 2) |
| 글자·값 | UTF-8 (BOM 없음), 줄 끝 CRLF, 빈칸 = NULL, `true`/`false`, 날짜 `2026-09-01`, 날짜시각 `2026-09-01T08:00:00+09:00` |
| DB가 채우는 칸 | 물리 추가 칸(`is_active`, `password_hash`, `processor_roles` 등 기본값)·생성 칼럼(`duration_min`, `is_on_time` …)·`inventory_item.on_hand_qty`(거래 트리거). 빈칸인데 DB가 NOT NULL + 기본값이면 기본값 (예: `production_lot.scrap_qty` 빈칸 = 0) |
| 계산 칸 | `shift_report.availability_pct`(생성기는 넣지 않음, ERD "계산") → 넣을 때 `v_shift_equipment_kpi`로 계산해 저장. `maintenance_work_order.trigger_kind`(CSV에 있음) → DB는 계기 FK 세 칸으로 계산(`v_work_order.trigger_kind`) — 넣지 않고 **같은지 확인**, 다르면 멈춤 |
| 기준 정보 | "있으면 고치고 없으면 넣기" — 시드가 먼저 넣은 `role`·`notification_rule`(25행)도 생성기 값으로 덮되 물리 추가 칸(처리 방법·받는 역할·보고 순위)은 그대로 |
| 번호 | 일련번호는 생성기가 매김 → 적재 뒤 시퀀스를 최대값 + 1로. 업무 번호 카운터는 `fn_sync_doc_numbers()` (MW-0901·MR-0901·MR-S-0901 = 월 + 두 자리, PO-2609-001, MAT-2609-01, SHP-2609-001) |
| 사용자 | `U01`~`U12` (생성기 masters). `password_hash`는 비어 들어간다 → 개발·시연 비밀번호는 `tools/gen_dev_users.py --update` |
| 센서 | `sensor_sample.csv` 9월 약 98만 행·55MB(5초 `SEC5` + 1분 평균 `MIN1_AVG`) — **따로 넣는다** (`--sensor-only`). 저장소에 올리지 않음 (생성기 `generate.py`로 같은 seed면 같게 다시 만듦) |
| 10/1 리허설 | `out_realtime/`(권장 순서 대본 결과)는 선택 (`--realtime`). 번호는 9월 다음부터 붙고 작업지시·로트·검사 방식은 덮어쓴다. 시연 기준점(SIM-03)은 9월 끝(10/1 08:00)에서 만들어 두므로 **SIM-03을 누르면 리허설 기록은 사라진다** |

## 2. 넣는 순서와 방법

한 번에: `scripts/load_all.sh` (Docker·Supabase 준비도 같은 순서 — README "데이터 넣기").

```bash
PGDATABASE=mom ./db/apply.sh                                   # 1) 스키마 + 시드 (개발 목업 --dev 는 빼고)
psql -v app_password=… -v ai_password=… -f db/roles.sql       # 2) 앱·비서 계정 권한
python tools/load_generated.py <생성기> --psql "psql -d mom"    # 3) 기준 정보 22 + 9월 33 (+ 10/1 근무일·교대, 시연 기준점)
python tools/load_docs.py <11_automotive> --psql "psql -d mom"  # 4) 사내 문서 8개 → doc_chunk (+ 기준점 다시)
python tools/gen_dev_users.py --update <비밀번호> | psql -d mom   # 5) 개발·시연 비밀번호 (운영 금지)
psql -d mom -f db/checks/validate_loaded_data.sql              # 6) 점검 20개 — 모두 0이어야 함
python tools/load_generated.py <생성기> --psql "psql -d mom" --sensor-only   # 7) (선택) 센서 약 98만 행, 약 15초
```

3)이 하는 일:
1. 머리 줄을 확인한다 (1장). 어긋나면 멈춤.
2. 외래 키 순서로 정렬해(서로 가리키는 지연 FK는 순서에서 뺌, 계산 칸이 있는 `shift_report`는 맨 끝) **한 트랜잭션**에서 넣는다.
   - `app.loading = on`: 알림 NOTIFY·자동 알림(작업지시서 초안 검토 등)·폐기 수량 더하기를 끈다 — 과거 기록을 다시 만들지 않게.
     로트 상태 단계 확인(R-24a)도 끈다 (10/1 기록이 9월 끝 로트를 마지막 상태로 덮을 때).
   - `SET CONSTRAINTS ALL DEFERRED`: 작업지시서 ↔ 알림 같은 순환 참조는 커밋 때 확인.
   - CHECK·FK·고유·겹침 금지·역할 트리거는 **그대로 걸린다** — 규칙을 어긴 데이터는 들어가지 않는다.
3. 시퀀스·업무 번호 카운터, 알람 ↔ 관련 재고 품목(`fn_seed_alarm_related_items`), **지금 상태 칸**(`fn_sync_after_load`: 공구 누적 = 마지막 사용 기록 — masters는 9/1 시작 상태라서, 9/30 끝 T05 = 90%), **10/1 근무일·교대**(`fn_ensure_work_day` — 9월 기록에는 9/30까지만), 시연 시계 = SIM 10/1 08:00 멈춤, **시연 기준점**(`fn_demo_snapshot`, 센서는 복사하지 않고 되돌릴 때 기준점 뒤 값만 지움), `dataset_info`.
4. 줄 수가 manifest와 같은지 확인 (다르면 종료 코드 3).

트리거는 "상태가 바뀌는 순간"을 보므로, 과거 기록을 INSERT로 한꺼번에 넣은 데이터는 `validate_loaded_data.sql`로 확인한다:

## 5. CMM 측정 결과 파일 — `MOM-CMM-CSV v0.1` (DOC-06 Rev.2 §3.6)

사용자 폴더 `Claude outputs/`의 예시 3개(`tests/data/`에 그대로 복사)와 같은 모양이다.

```
#format,MOM-CMM-CSV v0.1
#cmm_id,CMM-01
#program,BRK-A100_OP50_ENH_R0
#lot_no,LOT-2609-038-1
#sample_no,F12
#insp_kind,ENHANCED
#operator,U06
#measured_at,2026-09-15T15:10:44+09:00
#room_temp_c,20.3
#part_temp_c,20.9
#temp_comp,ON
char_no,char_name,position,nominal,upper_tol,lower_tol,actual,deviation,cmm_judgement,unit
1,부싱 압입 구멍 지름 Ø45 H7,TOP,45.000,0.025,0.000,45.021,0.021,PASS,mm
```

| 부분 | 약속 |
|---|---|
| 머리 줄 `#키,값` | 필수: `lot_no`(LOT-YYMM-NNN-n), `insp_kind`(FIRST·SAMPLE·ENHANCED 또는 초품·발췌·강화). 선택: `part_seq`, `sample_no`, `cmm_id`, `program`, `operator`, `measured_at`·`measure_start_at`·`measure_end_at`(시간대 필수), `room_temp_c`·`part_temp_c`·`machine_temp_c`, `temp_comp`(ON·OFF·켬·끔). 모르는 키도 `raw_header`에 그대로 남긴다 |
| 표 열 | 필수: `char_no`(검사 항목 번호), `actual`, `cmm_judgement`(PASS·FAIL·OK·NG·합격·불합격). 선택: `char_name`, `position`(STD·TOP·MID·BOT, 빈칸 = STD), `nominal`, `upper_tol`, `lower_tol`, `deviation`, `unit` |
| 숫자 | 글자 그대로 저장 (소수 자릿수 유지) |
| 한 파일 | 같은 항목·위치 줄이 두 번 있으면 양식 오류 |
| 인코딩 | UTF-8(BOM 허용) 또는 CP949 [확인 필요: 실제 측정기 소프트웨어] |
| 파일 이름 [제안] | `{cmm_id}_{lot_no}_{sample_no}_{insp_kind}_{yyyymmddHHMMSS}.csv` — 재측정 때 겹치지 않게 측정 끝 시각. 같은 이름이 또 오면 `#2`를 붙여 따로 남긴다 |

처리 결과 (`cmm_import.status`):

| 결과 | 언제 | 파일 | 알림 |
|---|---|---|---|
| `SUCCESS` | 양식 OK + 열린 측정 지시와 맞음 + 항목 다 있음 | processed | — |
| `NEEDS_CHECK` / `LOT_MISMATCH` | 지시와 다름 (로트·순번·검사 방식) | processed (값은 기록, 확인 필요 표시) | `CMM_FILE_ERROR` (확인 필요) |
| `NEEDS_CHECK` / `INCOMPLETE` | 빠진 항목 | processed | `CMM_FILE_ERROR` (확인 필요) |
| `FAILED` / `FORMAT` | 머리·열 빠짐, 숫자 아님, 모르는 값, 인코딩 | error (DB에 측정값 없음) | `CMM_FILE_ERROR` |
| `FAILED` / `LOT_MISMATCH` | 없는 로트, 측정자를 알 수 없음(측정 시작 기록도 없고 operator도 작업자 계정이 아님) | error | `CMM_FILE_ERROR` |

측정기 판정(`cmm_judgement`)과 서버가 공차로 다시 계산한 판정(`judgement`)이 다르면 그 값은 확인 필요가 되고 `CMM_JUDGE_MISMATCH` 알림. 재측정 값(같은 부품·항목 두 번째부터)도 확인 필요 — 판정에 쓸 값은 반장이 고른다 (R-81).

**[선택 필요] 부품 순번**: 예시 파일에는 순번 칸이 없고 `sample_no`(S01·S06·F12)만 있다. 지금은 ① 머리에 `part_seq`가 있으면 그것, ② 없으면 `sample_no` 끝 숫자를 부품 순번으로 본다. 목업 지시(초품 1번, 발췌 5번)로 예시를 넣어 보면 S01 = SUCCESS, S06·F12 = NEEDS_CHECK(LOT_MISMATCH)가 된다. 측정기 쪽에 `#part_seq` 줄을 넣는 것이 가장 깔끔하다.

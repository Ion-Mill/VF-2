# DB 담당 전달: 브리핑 체크 표 `briefing_check` 올리기 (2026-10-20)

> 보낸 사람: 화면·백엔드 코드를 고친 쪽 · 받는 사람: DB 담당 (공용 Supabase `mom-db`)
> 부탁은 하나다. **새 표 1개를 공용 DB에 올려 주세요.** 코드는 이미 만들어 두었고, 공용 DB는 DB 담당만 고치기로 한 규칙이라 표만 비어 있다.
> 화면·백엔드 변경 내용은 `구현_중_수정사항/1020_수정간단내용.md` 35장에 있다.

## 1. 한눈에 보기

| 묻는 것 | 답 |
|---|---|
| 왜 필요한가 | 이브 브리핑의 "먼저 챙길 일"에서 체크하고 창을 닫았다 열면 체크가 모두 풀렸다. 체크를 서버에 남기려는 것이다 |
| 올릴 것 | 표 1개 `briefing_check` (4칸) + 권한·RLS 정책 + 시연 되돌리기 목록에 이름 추가 |
| 올릴 파일 | `backend/supabase/migrations/20261020010000_briefing_check.sql` (30줄, 이 파일 하나) |
| 누가, 어떤 계정으로 | DB 담당이, 스키마 주인 계정(`postgres`)으로 한 번 |
| 걸리는 시간·멈춤 | 표 1개 만들기뿐이라 1초 안. 서버를 멈출 필요 없음 |
| 기존 데이터 | 바꾸거나 지우는 것 없음 (새 표만 만듦) |
| 두 번 돌려도 되나 | 된다. 표는 `IF NOT EXISTS`, 정책은 지우고 다시 만든다. 로컬에서 두 번 돌려 오류 0 확인 |
| 안 올리면 | 새 API(`/api/assistant/briefing/checks`)만 오류가 나고, 화면은 이 브라우저에 저장해 계속 동작한다. 다른 기능은 영향 없음 |

## 2. 표 모양

| 칸 | 형식 | 설명 |
|---|---|---|
| `user_id` | varchar(20), 필수 | 체크한 사람 (`app_user` 참조) |
| `shift_id` | varchar(40), 필수 | 브리핑의 교대. 화면이 `r<시연 회차>/<교대 번호>` 모양으로 보냄 |
| `item_key` | varchar(120), 필수 | "먼저 챙길 일" 항목 글자. 화면이 정하고 서버는 뜻을 모름 |
| `checked_at` | timestamptz, 필수 | 체크한 때 (시연 시계 `app_now()`) |

- 기본키는 (`user_id`, `shift_id`, `item_key`) 3칸이다. `shift_id`·`item_key`는 빈 글자나 공백뿐인 글자를 넣을 수 없다.
- **외래 키는 `app_user` 하나뿐이다.** `shift`나 알림·알람 표와 잇지 않는다. 항목이 알람·알림·예방 정비·인계·잠금으로 여러 곳에서 오고 일부는 화면 계산이라 서버가 뜻을 알 수 없기 때문이다.
- 체크는 개인 메모일 뿐 알림·알람의 처리 상태를 바꾸지 않는다.

## 3. 파일이 하는 일 (순서대로)

|---|---|
| 1 | 표 `briefing_check` 만들기 (`IF NOT EXISTS`) |

| 4 | 시연 "처음으로"(`fn_demo_reset`)가 이 표도 비우도록 `demo_snapshot.briefing_check`를 만들고 `demo_snapshot.meta.tables`에 이름을 더함 |

## 4. 올리는 방법

둘 중 하나를 쓴다. 먼저 `psql`이 편하면 1번, 이전에 `check_request_1020`을 올린 방식이면 2번.

1. **SQL 편집기·`psql`:** 스키마 주인으로 접속해 파일을 그대로 실행한다. 비밀번호·접속 주소는 이 문서에 쓰지 않는다.
   ```
   psql "<접속 주소>" -v ON_ERROR_STOP=1 -f backend/supabase/migrations/20261020010000_briefing_check.sql
   ```
2. **연결 도구 `apply_migration`:** 이름 `briefing_check`, 내용은 같은 파일.

올린 뒤 `backend/supabase/README.md`의 마이그레이션 기록 칸(지금 10개 → 11개)을 고쳐 주세요. 이 저장소의 해당 줄에는 "공용 mom-db에는 아직 적용하지 않음"이라고 적어 두었다.

## 5. 올린 뒤 확인 (읽기만, 5개)

아래가 모두 맞으면 된다.

```sql
-- ① 표가 있고 4칸이다 → 4
SELECT count(*) FROM information_schema.columns WHERE table_schema='public' AND table_name='briefing_check';
-- ② RLS가 켜져 있다 → true
SELECT relrowsecurity FROM pg_class WHERE oid = 'public.briefing_check'::regclass;
-- ③ 정책 2개 → 2
SELECT count(*) FROM pg_policies WHERE schemaname='public' AND tablename='briefing_check';
-- ④ 권한: 앱 계정은 쓸 수 있고 비서 읽기 계정은 못 읽는다 → t | f
SELECT has_table_privilege('mom_app','public.briefing_check','INSERT'), has_table_privilege('mom_ai_ro','public.briefing_check','SELECT');
-- ⑤ 시연 되돌리기 목록에 들어갔다 → true
SELECT 'briefing_check' = ANY (tables) FROM demo_snapshot.meta;
```

참고: 로컬에서 "이미 올린 DB와 같은 상태(`db/` 원본 + 계정 + 시연 기준점)"에 이 파일을 올려 ②~⑤가 위와 같게 나옴을 확인했고, 표 모양이 처음부터 새로 만든 DB와 같음도 확인했다. RLS·정책만 잠그기 몫으로 더 붙는 것이 다르다.

## 6. 주의할 점

- **표 하나만 만든다.** 다른 표·함수·권한은 건드리지 않는다. 그래도 올리기 전에 공용 DB의 백업이나 복구 지점이 있는지는 담당 판단에 맡긴다.
- **시연 기준점이 이미 만들어져 있어도 괜찮다.** 파일이 `demo_snapshot` 쪽에 빈 복사본을 만들고 목록에 이름을 더한다. 이 목록에 없으면 "처음으로"가 이 표를 비우지 않는데, 화면이 키 앞에 시연 회차(`r<번호>/`)를 붙이므로 옛 체크가 되살아나지는 않는다.
- **올리는 것만으로 공용 DB에 데이터가 생기지는 않는다.** 행은 사용자가 브리핑에서 체크를 누를 때 쌓인다 (한 번에 1행, 항목 글자와 시각뿐). 채팅 기록과 같은 종류의 개인 기록이다. 체크마다 `access_log`에도 API 접속 기록이 한 줄 남는다.
- **되돌리기:** 아래 3줄. 쌓인 체크는 함께 사라진다 (개인 메모라 잃어도 업무 영향 없음).
  ```sql
  DROP TABLE IF EXISTS public.briefing_check;
  DROP TABLE IF EXISTS demo_snapshot.briefing_check;
  UPDATE demo_snapshot.meta SET tables = array_remove(tables, 'briefing_check');
  ```

## 7. 올리는 시점과 순서

- 코드가 합쳐지기 전·후 어느 쪽에 올려도 된다. 표가 먼저 있어도 옛 코드는 쓰지 않아 무해하고, 코드가 먼저 합쳐지면 표가 올라올 때까지 새 API만 오류다.
- 화면이 서버 저장을 쓰려면 화면 서버에 `NEXT_PUBLIC_MOM_API`(백엔드 주소)가 있어야 한다. 이미 채팅에 쓰고 있어 대부분 켜져 있다.
- 백엔드(8020)는 코드가 합쳐진 뒤 다시 켜야 새 API가 열린다. 이 재시작은 코드 쪽에서 한다 (DB 담당 할 일 아님).
- 표가 생긴 뒤 처음 브리핑을 열 때, 그 전에 한 브라우저에서만 해 둔 체크가 한 번 풀릴 수 있다 (서버 값을 따르기 때문). 알아 두면 된다.

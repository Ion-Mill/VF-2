# DB 담당 전달 — 채팅 센서 값이 화면의 실시간 값과 다른 문제 (2026-10-21)

> 보낸 사람: AI 비서(`assistant/`) 담당 · 받는 사람: 백엔드·DB 담당
> 시연 채팅에서 보전 담당자가 `VF2-01 센서 추세`를 물으면 공용 DB의 센서 값을 읽어 답하는데, 화면(시연 서버)에 보이는 값과 크게 달랐다. 비서는 시연용 임시 방식으로 화면과 같은 값을 답하게 했고, 근본 해결은 DB 쪽 결정이 필요하다.
> 백엔드·DB 코드는 아무것도 고치지 않았다.

## 요약

| 항목 | 내용 |
|---|---|
| 증상 | 같은 시각에 채팅 `주축 부하 마지막 1.1%`(공용 DB, 10/1 08:00 기준) ↔ 화면 `41.8%`(시연 서버, 10/1 13:43). 주축 모터 온도 28.4℃ ↔ 37.4℃, X·Y·Z축 부하도 크게 다름 |
| 원인 | 채팅은 도구 `sensor_trend`로 공용 DB를 읽는데 `sim_clock`이 10/1 08:00에 멈춰 있고 센서 표본이 그 시각 이후로 쌓이지 않는다. 시연 서버는 자기 시계로 센서 값을 따로 만들어 화면에만 보낸다 (`GET /api/line/twin`의 `equipment[].sensor`). 두 곳이 이어져 있지 않다 |
| 비서가 한 것 | 스위치 `SENSOR_LIVE=1`(코드 기본 꺼짐)이면 `sensor_trend`의 권한·이름·단위·정상 범위는 그대로 공용 DB에서 쓰고, 값만 시연 서버의 지금 값으로 바꿔 답한다. 답 머리에 "시연 화면 시계 · 지금 값"이라고 밝히고, 최소·평균·최대는 한 점이라 없다. 시연 서버를 못 읽으면 공용 DB 값으로 답한다 |
| 한계 | 지난 시간의 변화(추세)는 못 보여 준다. 시연 서버의 값은 가상 값이고, DB에 쌓이지 않는다 |
| 급한 정도 | 낮음 — 시연은 임시 방식으로 가능하다. 정식 구조로 가려면 아래 선택지가 필요하다 |

## 1. 확인 질문

1. 공용 DB `sim_clock`이 10/1 08:00에 멈춘 것은 의도된 동작이 맞나? (앞선 전달 문서 `DB담당_전달_정비이력_기간필터_20261021.md` 2장과 같은 질문)
2. 시연 서버의 센서 값(1분마다 2건)을 DB `sensor_reading` 같은 표에 넣는 길이 있나, 아니면 화면 전용인가?

## 2. 정식으로 맞출 때의 선택지 (제안)

| 선택지 | 내용 | 비고 |
|---|---|---|
| A | 시연 서버가 센서 표본도 DB로 보내고(`/api/ingest/...`) DB 시계가 시연 시계를 따라간다 | 채팅·리플레이·보고서가 같은 값을 보게 된다. 공용 DB 쓰기라 보호 규칙(공용DB_보호)을 따라야 한다 |
| B | 지금처럼 채팅이 시연 서버의 지금 값을 읽는다 (비서가 이미 함) | 시연용 임시 방식. 과거 추세는 없다 |
| C | 시연에서는 DB 값 그대로 두고 "10/1 08:00 기준"만 밝힌다 | 가장 작지만 화면과 다르다 |

권장: 시연은 B(이미 적용), 정식 구조는 A.

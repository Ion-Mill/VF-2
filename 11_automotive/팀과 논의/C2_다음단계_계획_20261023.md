## 2. 꼭 지킬 규칙 (두 번 생기거나 두 번 빠지지 않게)

| # | 규칙 | 이유 |
|---|---|---|
| 1 | 백엔드 모드에서는 화면의 **작업지시서 초안 만들기(`App.tsx` createWo)를 끈다** | DB가 정지 알람마다 초안을 이미 만든다 → 켜 두면 두 장 |
| 2 | 백엔드 모드에서는 `rules.ts` `derive`·`fromEvents`가 만드는 알림을 끄고 **`/api/notifications`만 보인다** (같은 규칙 코드라 화면 모양은 그대로) | DB 규칙과 화면 규칙이 같은 알림을 따로 만든다 |
| 3 | 작업기록서·간이 기록을 백엔드로 옮기는 **같은 때에** 화면의 재고 사용(`inventory/txns` USE) 호출을 지운다 | 백엔드가 확정 때 뺀다 → 둘 다 하면 두 번 (지금 1단계는 USE를 보내지 않아 정비 소모품이 안 빠짐) |
| 4 | 시뮬레이터가 주인인 일은 지금처럼 백엔드 → 시뮬레이터 (작업기록서 확정 뒤 `/api/sim/work-record-confirmed`) | DB 중계가 같은 표를 덮어쓴다 |
| 5 | 번호를 화면이 만들지 않는다 (`MW-0950+` 등) — DB 번호를 그대로 | 여러 사람이 같은 DB를 본다 ("DB 1개 = 공장 1개") |
| 6 | 상태 이름을 한 곳에서 바꾼다 (화면 `draft/editing/approved/inprogress/done` ↔ DB `AI_DRAFT/EDITING/APPROVED/IN_PROGRESS/DONE`) | `backendApi.ts` 한 곳 |

## 3. 순서 (한 묶음씩, 묶음마다 스위치를 켠 채 확인)

| 순서 | 묶음 | 확인 |
|---|---|---|
| 1 | 알림: `/api/notifications` 읽기·읽음·확인·처리, 화면 규칙 알림 끄기 | 반장·보전·작업자 각자 받는 알림이 시연 서버 모드와 같은 종류인지 (`backend_adapter_check.mjs`에 알림 대조 더하기) |
| 2 | 작업지시서: 목록·상세·고치기·배정·승인·시작 (초안은 DB) | S1 → 초안 1장(두 장 아님), 반장만 승인 |
| 3 | 작업기록서·간이 기록: 만들기·고치기·잠금 9단계·확정·반장 확인, 확정 뒤 설비 복귀, 재고 USE 호출 지움 | 확정 한 번에 부품 재고가 한 번만 빠짐, 설비가 다시 돔 |
| 4 | 정지 사유 입력·확정, 예방 정비 초안 확인 | |
| 5 | 비서 문장 다듬기(`assist/*`)를 백엔드 비서 입구로 (지금은 기본 문장) | 꺼져 있으면 기본 문장 그대로 |
| 6 | 스위치 기본값을 백엔드로 → 시연 서버의 임시 백엔드 부분(`server_live.py` 화면 계산) 지우기 | 시연 리허설 한 번 |

## 4. 1단계에서 남긴 작은 차이 (같이 정리)

- 짧은 정지 수(`production.short_stops`)가 0 — 백엔드 계산 더하기
- 라인 고장 손실: 백엔드는 5분 미만 정지도 셈, 시연 서버는 5분 이상만 (DOC-07 기준 확인 뒤 한쪽으로)
- 진행 중인 교대의 보고서 초안: 시연 서버는 진행 중에도 계산해 보여 줌, 백엔드는 교대 끝에 스케줄러가 만듦
- 재공·완제품 시각: DB 기록 간격(재공 5분, 실적 줄 단위)이라 다시 보기가 덜 촘촘
- **생산 시간대별 누계·예측**: DB 실적(`operation_report`)은 로트 × 공정 × 설비 × 교대 줄이라, 한 로트의 OP-50 합격이 줄이 끝나는 시각에 몰린다 → 그래프 계단·예측이 시연 서버와 다름(10:30 예측 182 vs 110). 줄의 합격 수를 시작~끝 사이에 고르게 나눠 세거나(어림), 부품별 완료 시각을 남기는 방법 중 고른다 [선택 필요: DB 담당]

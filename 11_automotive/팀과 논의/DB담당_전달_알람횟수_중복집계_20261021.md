# DB 담당 전달 — 알람 횟수 중복 집계 (2026-10-21)

> 보낸 사람: AI 비서(`assistant/`) 담당 · 받는 사람: 백엔드·DB 담당
> 시연 채팅에서 알람 횟수가 실제보다 1번 많게 나온다. 원인은 비서가 아니라 `backend/app/sql/assistant.sql`의 `alarms` 조회 한 곳이다.
> 백엔드·DB 코드는 아무것도 고치지 않았다. 고치면 비서·화면은 값을 그대로 보여 주므로 따로 손볼 곳이 없다.

## 요약

| 항목 | 내용 |
|---|---|
| 증상 | 알람 2075의 30일 횟수가 **10번**으로 나온다 (실제 **9번**). 설비별로는 VF2-02가 **5번**으로 나온다 (실제 **4번**) |
| 원인 | `alarm_event`에 `equipment_state_log`를 LEFT JOIN한 채 `count(*)`로 센다. 상태 기록이 2줄인 알람이 2번 세어진다 |
| 부탁 | `count(*)` → `count(DISTINCT a.alarm_event_id)` 한 줄 수정 (아래 3장) |
| 영향 | 비서의 "몇 번 났어?" 답, 알람 답 카드의 "이 알람은 최근 7일 N번, 30일 M번" 줄. 7일 값은 해당 알람이 없어 맞게 나온다 |
| 급한 정도 | 보통 — 숫자가 1 틀린다. 시연 대본의 "2075가 이번 주 세 번째" 같은 7일 값은 영향 없음 |

## 1. 증상 (화면에서 본 값)

- `2075 몇 번 났어?` → "2026-09-01 ~ 2026-09-30 알람 2075 발생 / 1. VF2-01 5번 / 2. VF2-02 5번" (합계 10)
- 알람 답 카드 → "이 알람은 최근 7일 3번, 30일 10번 났습니다"
- 실제 (같은 DB를 읽기 전용으로 센 값): 2075는 9/2부터 9/30까지 **9건** — VF2-01 5건, VF2-02 4건. 7일(9/24~9/30)은 3건으로 맞다.

## 2. 원인

`backend/app/sql/assistant.sql`의 `-- name: alarms` (15행 근처):

```sql
SELECT a.equipment_id, a.alarm_code, m.name_ko, a.severity_at_event, count(*)::int AS times, ...
  FROM alarm_event a JOIN alarm_master m USING (alarm_code)
  LEFT JOIN equipment_state_log s ON s.alarm_event_id = a.alarm_event_id
 WHERE ...
 GROUP BY a.equipment_id, a.alarm_code, m.name_ko, a.severity_at_event
```

- 알람 1건에 상태 기록(`equipment_state_log`)이 **2줄**이면 JOIN 결과가 2줄이 되고 `count(*)`가 2를 센다.
- 이런 알람이 지금 **1건** 있다: `alarm_event_id = 20` (VF2-02, 알람 2075, 2026-09-02 16:54). 나머지 8건은 상태 기록이 1줄이다.
- `down_min`(정지 분)은 상태 기록 줄마다 한 번씩 더하므로 중복이 아니라 맞게 나온다. 틀리는 것은 **횟수(`times`)뿐**이다.
- 같은 모양(알람 이벤트 ↔ 상태 기록 JOIN + 횟수 세기)은 이 SQL 한 곳에서만 찾았다 (`alarms.sql`·`documents.sql`·`production.sql`의 상태 기록 JOIN은 알람 이벤트에 붙이는 쿼리가 아님).

## 3. 수정안

```sql
-- 전
count(*)::int AS times
-- 후
count(DISTINCT a.alarm_event_id)::int AS times
```

- 나머지 열(`first_at`·`last_at`·`down_min`)은 그대로 둔다.
- 정지 분도 이벤트 기준으로 더 정확히 하려면 `down_min`을 서브쿼리로 빼는 방법이 있으나, 지금은 틀리지 않아 건드릴 필요가 없다.

## 4. 확인 방법 (읽기 전용 SELECT)

```sql
-- 틀리는 값과 맞는 값 (기대: 10, 9)
SELECT count(*), count(DISTINCT a.alarm_event_id)
  FROM alarm_event a JOIN alarm_master m USING (alarm_code)
  LEFT JOIN equipment_state_log s ON s.alarm_event_id = a.alarm_event_id
 WHERE a.alarm_code = '2075'
   AND a.occurred_at >= '2026-09-01T00:00:00+09:00' AND a.occurred_at < '2026-10-01T00:00:00+09:00';

-- 상태 기록이 2줄 이상인 알람 (기대: alarm_event_id 20 한 건)
SELECT a.alarm_event_id, a.equipment_id, a.occurred_at, count(s.*)
  FROM alarm_event a LEFT JOIN equipment_state_log s ON s.alarm_event_id = a.alarm_event_id
 WHERE a.alarm_code = '2075' GROUP BY 1, 2, 3 HAVING count(s.*) <> 1;
```

수정 뒤 기대값: 30일 합계 9, VF2-01 5 / VF2-02 4.

## 5. 시험 제안

- 알람 이벤트 1건에 상태 기록 2줄이 붙은 자료로 `alarms` 조회를 부르면 `times`가 1인지 보는 시험 한 개.
- (참고) 비서 쪽은 이 값을 그대로 합산하므로 따로 시험을 더할 필요가 없다 (`assistant/backend/tests/`는 가짜 백엔드를 쓴다).

## 6. 우리가 한 일 / 하지 않은 일

- 한 일: 증상 확인, 원인 SQL 찾기, 읽기 전용 SELECT로 값 확인 (공용 DB에 쓰지 않음).
- 하지 않은 일: `backend/`·DB 변경, 비서에서 숫자를 보정하는 우회 코드 (다른 곳이 같은 SQL을 쓰면 또 틀리므로 원인을 고치는 쪽이 맞다).

**부탁**: 수정할지, 다른 방법을 쓸지 알려 주세요. 비서(8100)는 값을 저장하지 않고 매번 백엔드 조회 도구를 부르므로 다시 켤 필요가 없다. 백엔드(8020)를 다시 켜야 새 SQL을 읽는지는 SQL 읽는 방식에 달려 있어 우리가 확인하지 못했다 (담당자가 판단).

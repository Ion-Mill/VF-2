## 1. 주제 설명

### 1.1 한 줄 정의

> 알루미늄 자동차 부품을 깎는 가공 라인에서, **AI 운영 비서**가 설비와 생산 상황을 지켜보다가 알람이 뜨면 **"무엇이 문제인지 → 어떻게 점검하는지 → 어떻게 안전하게 작업하는지"** 를 공식 문서 근거와 함께 먼저 알려 주고, 작업지시서·정비 이력·교대 보고서까지 이어서 처리해 주는 플랫폼.

### 1.2 이 플랫폼은 "실시간 대시보드"인가?

**대시보드는 화면 하나일 뿐이고, 중심은 "사건이 생기면 비서가 다음 일을 줄줄이 처리하는 흐름"이다.**

| 구분 | 실시간 대시보드 | 이 플랫폼 |
|---|---|---|
| 보여 주는 것 | 지금 상태, 숫자, 차트 | 지금 상태 + **해야 할 일과 방법** |
| 알람이 뜨면 | 빨간색으로 바뀜 | 지침 카드, 안전 절차, 작업지시서 초안, 담당자 연락까지 이어짐 |
| 사람이 할 일 | 화면을 보고 스스로 판단 | 비서가 정리한 것을 확인하고 승인, 현장 작업 |
| 시간 | 지금 | 지금 + 지난 교대 보고 + 앞으로의 일정 |

### 1.3 운영 관리 플랫폼(MOM)이란

공장의 일을 국제 표준(ISA-95)은 크게 네 영역으로 나눈다. 이 플랫폼은 **정비와 생산**에 집중하고, 품질은 검사 기록 수준까지 다룬다.

| 영역 | 하는 일 | 이 플랫폼에서 |
|---|---|---|
| 정비 | 고장 대응, 예방 정비, 정비 이력, 공구 관리 | **중심 영역** |
| 생산 | 가동 현황, 작업지시, 생산 실적 | **중심 영역** |
| 품질 | 검사, 불량 관리 | 검사 기록·불량 집계 (권장) |
| 재고 | 자재, 예비 부품 | 작업지시서의 "필요 부품" 칸으로만 다룸 |

### 1.4 가상 공장 설정

| 항목 | 설정 | 구분 |
|---|---|---|
| 공장 | 자동차 부품 협력사의 절삭가공 공장 1곳, 라인 1개 | [가상] |
| 제품 | 파워트레인용 알루미늄(6061-T6) 브래킷 2종 | [가상] 제품, 재질은 실제 규격 |
| 근무 | 주간·야간 2교대, 월~토 | [가상] |
| 핵심 설비 | Haas VF-2 수직 머시닝센터 2대, 새 제어기(NGC) | 설비와 문서는 [실제] |
| 운영 데이터 | 설비 상태, 알람 발생, 작업지시, 정비 이력, 검사 결과 | [가상] |

> **NGC로 정한 이유:** 팀원 자료의 알람 135, 179는 구형 제어기 알람이라 새 VF-2에는 없다. NGC로 정하면 공식 알람 865개와 한국어 번역 809개를 그대로 쓸 수 있다. (탐색 보고서 3.6)

### 1.5 공정 흐름과 공정별로 다루는 정도

```
 원자재(알루미늄 봉)
   │
 OP-10 절단 ──▶ OP-20 황삭 ──▶ OP-30 정밀 가공 ──▶ OP-40 디버링·세척 ──▶ OP-50 측정 ──▶ 출하
 Haas HCS-80     3축 머시닝센터    Haas VF-2 ×2 대     세척기·텀블러          3차원 측정기
```

모든 공정을 플랫폼에서 다루기 위해 **"가상 사내 문서"** 를 만든다. 제조사 매뉴얼은 실제 문서만 쓰고, 회사가 직접 만드는 표준 작업서·검사 기준서만 실제 문서를 바탕으로 가상으로 작성한다. 각 문서에는 "가상 사내 문서"라고 표시한다.

| 공정 | 하는 일 | 설비 | 실제 자료 | 만들 가상 사내 문서 | 플랫폼에서 다루는 정도 |
|---|---|---|---|---|---|
| OP-10 | 봉재 절단 | Haas HCS-80 [실제 제품] | HCS-80 매뉴얼(알람 30개, 정비 장), KOSHA M-9-2023 둥근톱 지침 | 절단 표준 작업서 | 상태, 알람 카드(간단), 점검표 |
| OP-20 | 겉면·외곽 거친 가공 | 3축 머시닝센터, Siemens 840D sl 제어기 가정 | Siemens 알람 4,143개(**한국어**), KOSHA 밀링 안전 자료 | 황삭 표준 작업서 | 상태, 알람 카드 |
| **OP-30** | 포켓, 구멍 보링, M6 나사 | **Haas VF-2 2대** | Haas 문서 전체 | 정밀 가공 표준 작업서, 공구 수명 한도표, 알람 심각도 기준 | **모든 기능의 중심** |
| OP-40 | 버 제거, 세척 | 초음파 세척기, 텀블러 | 세척기 매뉴얼(문제 9개), KOSHA M-21-2012 절삭유 지침 | 세척 표준 작업서, 세척액 관리 기준 | 상태, 점검표, 문제 대응 |
| OP-50 | 치수 측정, 합격 판정 | 3차원 측정기 (제조사 이름 쓰지 않음) | 측정기 오류 코드 258개, NIST 실제 측정 결과 파일, 공차표 | **검사 기준서**, 관리계획서 | 검사 기록, 합격 판정, 오류 카드 |

- 공정 순서는 **팀이 정한 가상 공정**이다. 다만 실제 가공 공장 기록(4TU)도 "가공 → 검사 → 후가공 → 최종 검사" 구조라 형태는 현실적이다.
- 3주 안에 하려면 **알람 카드는 OP-30을 깊게, 나머지는 얕게** 만든다. 가상 사내 문서는 공정마다 1~2쪽이면 충분하다.
- 가상 사내 문서 목록과 작성 방법: [설계서 6장](가상데이터설계서_v1.md#6-가상-사내-문서)

### 1.6 왜 이 주제인가

| 기준 | 이 주제의 상태 | 근거 |
|---|---|---|
| 공식 고장 문서가 있나 | **매우 충분.** 알람 865개, 알람별 설명, 증상·원인·조치 표가 있는 안내 문서 | Haas 알람 목록, 고장 대응 안내 |
| 한국어 문서가 있나 | **있음.** 알람 번역 809개, 한국어 조작 매뉴얼 498쪽, KOSHA 문서 36개, Siemens 한국어 알람 매뉴얼 | `docs/haas/`, `docs/kosha/`, `docs/line/` |
| 알람 때 작업자가 몸으로 개입하나 | **뚜렷함.** 전원 차단, 잠금·표지, 회전체 말림 위험 | 산업안전보건기준 규칙 제92조, 제95조 |
| 설비 데이터를 꺼내는 공식 방식이 있나 | **있음.** MTConnect(포트 8082), Q 명령. 원시 데이터 표본에는 주축 모터 온도, 공기 압력, 직류 전압도 있음 | Haas 데이터 수집 안내, 원시 데이터 표본 |
| 지표 계산식의 공식 근거가 있나 | **있음.** 가동률, MTTR, OEE 등 | NIST 논문(ISO 22400 정리) |
| 실제 운영 데이터가 있나 | **없음.** 실제 공개 기록의 모양을 따라 가상으로 만든다 | [가상 운영 데이터 설계서](가상데이터설계서_v1.md) |

## 2. 진행 방향

### 2.1 다섯 가지 원칙

| # | 원칙 | 뜻 |
|---|---|---|
| 1 | **근거 없으면 답하지 않는다** | 비서의 답과 안내에는 문서 이름과 쪽(또는 절)을 붙인다. 문서에 없으면 "문서에 없음"이라고 말한다 |
| 2 | **숫자는 지어내지 않는다** | 알람 기준 온도·압력은 Haas 문서에 없으므로 만들지 않는다. 가상 값은 화면에 "가상"이라고 표시한다 |
| 3 | **계산은 코드가, 문장은 AI가** | 가동률·MTTR 같은 숫자는 프로그램이 계산하고, 비서는 그 숫자를 문장으로 옮긴다. 문장 속 숫자는 프로그램이 다시 확인한다 |
| 4 | **안전 절차는 항상 들어간다** | 정비가 필요한 알람의 카드와 작업지시서에는 잠금·표지 절차와 보호구가 고정 서식으로 붙는다 |
| 5 | **설비는 사람이 움직인다** | 비서는 설비를 원격으로 켜거나 설정을 바꾸지 않는다. 정비 중 다른 사람·시스템이 설비를 움직이지 못하게 하는 것이 잠금·표지의 목적이기 때문이다 (법 제92조, KOSHA B-M-25-2026) |

### 2.2 만드는 순서 (3주)

```
1주차  준비         문서 처리, 한국어 검색 시험, 가상 데이터(과거 30일), DB·API 명세, 화면 틀
2주차  각자 만들기   지침 카드·작업지시서·챗봇, 브리핑·보고서, 가동 현황 화면, 실시간 전송
3주차  잇기·시연     알람 → 카드 → 작업지시서 → 이력 → 보고서 연결, 권장 기능, 평가, 시연 연습
```

## 3. 주 사용자와 현장 문제

### 3.1 주 대상과 현장 문제

**주 대상: 자동차 부품을 깎는 중소 규모 협력사 (절삭가공 뿌리기업).**

**근거 자료** (파일: `docs/background/`)

| # | 현장 문제 | 숫자 | 출처 | 확인 수준 |
|---|---|---|---|---|
| 1 | 절삭가공은 법으로 정한 뿌리기술이다 | 2021.12 시행령 개정으로 뿌리기술 6대 → 14대. "정밀가공 부문 ①절삭가공" 추가 | 산업통상자원부 보도자료 (2021.12) | 원문 확인 |
| 2 | 작은 회사일수록 기술 인력을 구하기 어렵다 | 부족률 중소 3.0%, 중견 1.1%, 대규모 0.5%. 10~29인은 3.8%. 부족 인원 39,834명 중 **90.5%가 중소 규모** | 산업통상자원부·KIAT, 2025년 산업기술인력 수급 실태조사 (2024년 말 기준) | 원문 확인 |
| 3 | 중소기업 기술 인력이 더 빨리 늙는다 | 50대 이상 비중: 중소 19.5%, 중견 18.1%, 대규모 9.4% | 같은 조사 | 원문 확인 |

**근거로 말할 수 있는 것과 없는 것**

| 말할 수 있음 | 아직 말할 수 없음 (가정) |
|---|---|
| 중소 가공업체는 기술 인력을 구하기 더 어렵고, 인력이 더 빨리 늙는다 (2, 3) | "매뉴얼이 영어 PDF로 흩어져 있다" — 국내 조사를 찾지 못함 |

| **정비 중 사고**가 끼임 사망의 주된 상황이다 → 안전 절차를 기본으로 넣는 이유 (6, 7) | 한국 중소 가공업체의 정지 비용 — 찾지 못함 |
| 숙련 인력이 빠지면 복구가 느려진다 (8, 해외 자료) | |

- 인력 부족률 자체는 2~3%로 몇 년째 비슷하다. 그래서 "심각한 인력난"이라고 쓰기보다 **"규모별 격차와 고령화"** 로 쓰는 것이 정확하다.
- Siemens 자료는 세계 대기업 기준이다. 한국 중소 가공업체에 그대로 적용하면 안 되고 "해외 대형 공장 기준"이라고 밝혀 적는다.
- 4, 5, 7번은 기사로만 확인했다. 발표에서 중요하게 쓰려면 원문(중기부, 한국자동차산업협동조합, 고용노동부)을 다시 확인한다.
- 오른쪽 열의 두 가정은 **현장 인터뷰로 확인할 가정**으로 표시한다.

**문제 정의 (근거를 이은 문장)**

> 자동차 부품 절삭가공은 법으로 정한 뿌리기술이고, 이 일을 하는 중소 협력사는 대기업보다 기술 인력을 구하기 어렵고 인력도 더 빨리 늙고 있다. 설비 데이터와 AI 활용은 아직 초기 단계다. 그런데 제조업 끼임 사망의 약 60%가 정비·청소 중에 일어난다. 그래서 **숙련자가 없어도 알람에 올바르고 안전하게 대응하도록 돕는 도구**가 필요하다.

## 4. AI 운영 비서

### 4.1 비서가 하는 네 가지 일

| # | 하는 일 | 언제 | 예시 |
|---|---|---|---|
| ① | **먼저 알리기** | 사건이 생기거나 기한이 다가올 때 | "VF2-01에서 992 알람. 충돌 의심입니다. 지침 카드를 확인하세요" / "VF2-02 축 윤활유 탱크 점검이 3일 지났습니다" / "T05 공구가 수명의 90%입니다" |
| ② | **브리핑** | 교대 시작, 하루 시작 | 지난 교대 요약, 진행 중 작업지시와 지연, 오늘 예정된 예방 정비, 주의할 설비, 승인 대기 작업지시서 |
| ③ | **보고** | 교대 끝, 하루 끝, 요청할 때 | 생산·불량·정지·정비 요약 + 특이 사항 + 다음 교대에 넘길 일 |
| ④ | **답하고 덧붙이기** | 물을 때 | 답 + 출처 + 관련 정보: "이 알람은 이번 주 세 번째입니다. 지난번에는 모터 커넥터 절삭유 오염이 원인이었습니다(정비 이력 MW-0914)" |

### 4.2 비서가 답할 수 있는 질문의 종류

| 질문 종류 | 예시 | 답의 재료 | 방식 |
|---|---|---|---|
| 문서 질문 | "992 뜨면 뭐부터 봐?" "제어반 열기 전 얼마나 기다려?" | Haas 문서, KOSHA, 가상 사내 문서 | 문서 검색 후 답 + 출처 |
| 운영 질문 | "어제 야간에 VF2-01 몇 번 멈췄어?" "이번 주 MTTR은?" | 운영 DB | **정해진 조회 도구**를 비서가 골라 씀 |
| 섞인 질문 | "2075가 왜 자꾸 떠?" | 이력 + 정비 일정 + 문서 | 조회 도구 + 문서 검색 |

- 팀원 자료는 "데이터 질문 챗봇(자연어 → SQL)"을 3주 안에 안정화하기 어렵다고 제외했다. 같은 이유로 **비서가 SQL을 직접 쓰게 하지 않는다.** 대신 미리 만든 조회 도구 10여 개(설비 상태, 알람 목록, 지표, 작업지시, 정비 이력, 예방 정비 기한, 공구 수명 등) 중에서 비서가 골라 쓰게 한다. 이렇게 하면 운영 질문도 안전하게 답할 수 있다.

### 4.3 알림 규칙 (알림이 너무 많으면 아무도 안 본다)

| 중요도 | 예시 | 보내는 방식 |
|---|---|---|
| 긴급 | 정지 등급 알람 | 화면 팝업 + 소리, 해당 설비 작업자·보전 담당자에게 |
| 주의 | 주의 등급 알람, 기한 넘긴 예방 정비, 공구 수명 90% | 알림 목록 + 브리핑에 포함 |
| 참고 | 조작 안내 알람, 일반 통계 | 브리핑·보고서에만 |

- 같은 알람이 짧은 시간에 반복되면 하나로 묶어서 알린다.

## 5. 비서의 행동 범위: 두 가지 안 [선택 필요]

**두 안 모두 공통:** 설비를 원격으로 켜고 끄거나 설정을 바꾸지 않는다. 잠금·표지, 점검, 부품 교체, 재가동은 사람이 한다. 설비는 위험할 때 이미 스스로 멈춘다(Haas 알람 설명의 "서보 꺼짐", "모든 기계 운동이 정지" 등).

차이는 **시스템 안의 기록과 서류를 비서가 알아서 바꾸느냐**이다.

### 5.1 두 안의 정의

| 구분 | 안 A — 알리고 돕는 비서 | 안 B — 시스템 안의 일은 자동 처리 후 보고 |
|---|---|---|
| 한 줄 | 비서는 알리고, 정리하고, 초안을 **보여 준다.** 기록을 바꾸는 것은 사람이 버튼을 눌러야 한다 | 비서가 시스템 안의 일을 **먼저 처리하고** 사람에게 보고한다. 결과가 큰 일만 승인을 받는다 |
| 사람의 일 | 확인 → 버튼 → 승인 → 현장 작업 | 보고 확인 → (필요시) 승인 → 현장 작업 |

### 5.2 일별 처리 방식 비교

| 일 | 안 A | 안 B |
|---|---|---|
| 지침 카드 표시 | 자동 | 자동 |
| 정지 사유 분류 | 비서가 추천, 작업자가 선택 | **자동 분류**, 작업자가 틀리면 고침 |
| 정비 작업지시서 | [작업지시서 만들기] 누르면 초안 | **자동으로 초안 생성** |
| 담당 보전원 지정 | 반장이 지정 | **자동 지정** (교대·담당 설비 기준), 반장에게 보고 |
| 의심 로트 보류 | 비서가 제안 | **자동 "보류" 표시**, 해제는 승인 필요 |
| 예방 정비 일정 등록 | 기한 알림만 | **자동으로 작업지시 등록** |
| 교대 보고서 | 반장이 [만들기] → 확인 → 발행 | **자동 생성·발행**, 반장이 고칠 수 있음 |
| 작업지시서 승인, 정비 완료, 보류 해제 | 사람 | 사람 (두 안 같음) |
| 설비 조작, 잠금·표지, 정비 | 사람 | 사람 (두 안 같음) |

### 5.3 장단점 비교

| 기준 | 안 A | 안 B |
|---|---|---|
| 만들기 난이도 | 낮음 | 중간. 자동 규칙표, **실행 기록, 되돌리기** 기능이 더 필요 |
| 3주 일정 | 여유 있음 | 빠듯함. 비서 동작 담당의 일이 늘어남 |
| 시연 인상 | "똑똑한 도우미" | "알아서 일하는 비서". 더 인상적 |
| 잘못 처리할 위험 | 거의 없음 (사람이 눌러야 바뀜) | 있음. 잘못된 자동 분류·지정이 기록에 남을 수 있음 → 되돌리기, "자동 처리" 표시 필요 |
| 현장 받아들임 | 쉬움 | 책임 소재 정리가 필요 (자동 지정된 일을 누가 책임지나) |
| 심사에서 받을 질문 | "그냥 챗봇 아닌가요?" | "잘못 자동 처리하면요?" |
| 추가로 만들 것 | 없음 | 자동 처리 규칙표, 처리 기록(누가·언제·무엇을), 되돌리기 버튼, 자동 처리 알림함 |

### 5.4 중간안

두 안을 섞을 수도 있다. 예: **작업지시서 초안과 교대 보고서는 자동(안 B), 담당 지정과 로트 보류는 제안(안 A).** 결과가 되돌리기 쉬운 일만 자동으로 하는 방식이다. 3주 일정에는 이 중간안이 가장 무리가 적다.

> 팀이 고른 안에 따라 8장 기능 상세의 "안 A / 안 B" 표시가 달라진다. 고르기 전까지는 두 안을 함께 적어 두었다.

| 자동 처리 | 사용자가 직접 설정하는 자동화 규칙이 따로 있음 | 안 B에서 규칙 + 처리 기록 + 되돌리기 |
| 언어·법령 | 영어 | 한국어, 국내 법령·KOSHA |

**가장 가까운 연구:** Park 외(2025)는 LLM 여러 개가 공작기계 매뉴얼을 읽고 CNC 알람을 해석해 조작 순서로 바꾸는 연구다. 실제 CNC 조작 화면에서 실행했다. 이 플랫폼과 달리 **설비 조작까지 자동화**하는 방향이고, 안전 절차는 다루지 않는다.

**조사한 범위에서 찾지 못한 조합**

1. 공식 제조사 문서를 인용한 알람 지침 카드
2. 국내 KOSHA 잠금·표지 절차를 **반드시** 넣는 정비 작업지시서
3. 교대 시작·끝 브리핑
4. 한국어, CNC 라인

이 네 가지를 한 도구에서 함께 하는 제품이나 연구는 이번 조사에서 찾지 못했다. LLM과 잠금·표지를 함께 다룬 연구는 사고 보고서 분석(Sabetta 외, 2025) 하나뿐이었다.

> 발표에서는 "이런 것이 없다"고 말하지 않는다. **"공식 문서 인용 + 잠금·표지 강제 + 교대 브리핑을 한국어 CNC 라인에 묶은 사례는 이번 조사에서 찾지 못했다"** 고 말하고, MachineMetrics와 Park 외(2025)를 가장 가까운 사례로 먼저 소개한다.

**이 플랫폼의 차별점 정리**

| # | 차별점 | 비교 대상과의 차이 |
|---|---|---|
| 1 | **안전 절차를 AI가 아닌 고정 서식으로 강제** | 다른 제품은 안전 질문에 답하거나 안전 항목을 앞에 정렬하는 정도 |
| 2 | **제조사 공식 문서만 인용** | 다른 제품은 사용자가 올린 문서를 쓴다 (품질이 회사마다 다름) |

### AST-01 교대 시작 브리핑

| 항목 | 내용 |
|---|---|
| 하는 일 | 교대가 시작되면 반장·보전 담당자에게 "지난 교대에 무슨 일이 있었고, 이번 교대에 무엇을 챙겨야 하는지"를 1분 안에 읽을 분량으로 정리해 준다 |
| 입력 | 지난 교대 보고서, 진행 중 작업지시, 미해결 알람, 오늘 기한인 예방 정비, 공구 수명 90% 이상 공구, 승인 대기 작업지시서 |
| 출력 | 브리핑 카드 (화면 첫 장 + 알림) |
| AI | 숫자와 목록은 프로그램이 모으고, 비서는 "가장 먼저 챙길 3가지"를 문장으로 정리 |
| 안 A / 안 B | A: 브리핑에 "할 일 목록" / B: "이미 처리한 일(자동 등록된 작업지시 등)" + "남은 할 일" |

| 브리핑 칸 | 예시 |
|---|---|
| 지난 교대 요약 | 생산 162개, 불량 1개, VF2-01 정지 2회(총 48분) |
| 먼저 챙길 일 | ① VF2-01 992 정비 작업지시 승인 대기 ② VF2-02 축 윤활유 점검 기한 3일 지남 ③ T05 공구 수명 92% |
| 오늘 예정 | 예방 정비 4건, 작업지시 4건 (PO-2609-041~044) |
| 출처 | 각 항목에 해당 기록 번호 링크 |

**근거:** 형식은 팀 설계. 들어가는 숫자의 계산식은 NIST 논문.
**더미:** 가상 운영 데이터 전체 ([설계서 5장](가상데이터설계서_v1.md#5-데이터별-만드는-방법)).

### PRD-01 가동 현황·정지 분석 화면

| 항목 | 내용 |
|---|---|
| 하는 일 | 설비별 지금 상태(색), 오늘 가동률, 정지 시간과 원인 순위, MTTR·MTBF·OEE를 보여 준다 |
| AI | 사용하지 않음. 화면 옆 비서 창에서 "이 차트 설명해 줘"는 가능 |
| 화면 | ① 라인 배치도 + 설비 상태 색 ② 설비별 상태 시간 막대 ③ 정지 원인 순위 ④ 지표 카드 ⑤ 작업지시 진행(PRD-03) |

**설비 상태 코드** [가상, 실제 방식에 맞춤]

| 플랫폼 상태 | 색 | 실제 데이터의 어떤 값에 해당하나 |
|---|---|---|
| RUN 가공 중 | 초록 | MTConnect 실행 상태 ACTIVE, Haas Q500 응답의 BUSY |
| IDLE 대기 | 노랑 | READY, Haas IDLE |
| SETUP 준비 | 파랑 | 작업자 입력 (공구 교환, 원점 세팅) |
| DOWN 고장 정지 | 빨강 | STOPPED + 정지 등급 알람 |
| MAINT 계획 정비 | 회색 | 예방 정비 작업 진행 중 |

**정지 사유 그룹:** 고장, 자재, 준비, 조작, 계획 ([설계서 5.8](가상데이터설계서_v1.md#58-정지-사유-downtime_reason)). 팀원 자료의 "기어박스 윤활 압력" 코드는 표준 VF-2에 기어박스가 없으므로 "축 윤활 이상"으로 바꾼다.

**지표 계산식** [실제, NIST 논문의 ISO 22400 정리]

| 지표 | 식 |
|---|---|
| 가동률 A | 실제 가공 시간 ÷ 계획 가동 시간 |
| 성능 E | 계획 사이클 시간 × 생산 수량 ÷ 실제 가공 시간 |
| 양품률 QBR | (양품 + 재작업 양품) ÷ 생산 수량 |
| OEE | A × E × QBR |
| MTTR | 수리 시간 합 ÷ 고장 횟수 |
| MTBF | 고장 간격 시간 합 ÷ 고장 횟수 |
| 고장 정비 비율 | 고장 정비 시간 ÷ (고장 정비 + 예방 정비 시간) |

- 팀원 자료의 "MTBF = 실제 가공 시간 ÷ 고장 횟수"는 쓰지 않는다. 논문은 이것을 별도 지표로 구분한다.
- 경고 기준("가동률 80% 미만", "MTTR 45분 초과")은 근거 문서가 없다. **팀이 정한 가상 기준**으로 표시한다.

### 10.1 구성도

```

                     │ REST API + 실시간 알림(SSE)
┌────────────────────▼──────────────────────┐
│ 백엔드 서버                                    │
│  ├ 운영 기능: 상태·알람·작업지시·지표 계산        │

        │               │              │
  ┌─────▼─────┐   ┌─────▼──────┐  ┌────▼─────┐
  │ 운영 DB    │   │ 문서 검색 DB │  │ 공구 수명 모델│
  └───────────┘   └─────▲──────┘  └──────────┘
                        │
                  문서 처리 (PDF·웹 문서 → 글자 → 조각)
                        │

```

### 10.2 기술 선택 [제안 — 팀 확정 필요]

| 부분 | 제안 | 이유 |
|---|---|---|
| 화면 | React + TypeScript | 팀원 자료의 화면 코드가 React 기준 |
| 백엔드 | Python (FastAPI) | AI·ML 담당과 같은 언어. 가상 데이터 생성기도 Python |
| 운영 DB | PostgreSQL | 팀원 자료의 DB 설계가 PostgreSQL 기준 |
| 문서 검색 DB | PostgreSQL 확장(pgvector) 또는 Chroma | DB를 하나로 줄이려면 pgvector |
| 실시간 알림 | SSE (서버 → 화면 한 방향) | 알림만 필요해서 WebSocket보다 간단 |
| 비서 | LLM API + 도구 호출(조회 도구) | 운영 질문을 SQL 없이 답하기 위해 |
| LLM | 팀이 쓸 수 있는 API | **한국어 질문 + 영어 문서**, 도구 호출을 잘 하는지 1주차에 시험 후 결정 |
| 임베딩 | 다국어 모델 | 한국어 질문으로 영어 문서를 찾아야 함 |
| 공구 수명 모델 | LightGBM (이전 분석에서 가장 좋았음) | `8_Haas_VF-1_milling` 분석 결과 |
| 문서 처리 | pypdf (이미 사용 중), 그림 PDF는 OCR | KOSHA 문서 5개는 그림이라 글자가 안 나옴 |
| 실행 환경 | Docker Compose | 5명이 같은 환경에서 실행 |
| 협업 | Git (비공개 저장소), API 명세 먼저 작성 | 화면과 서버를 동시에 개발 |

### 10.3 개발에 필요한 환경

| 1 | 한국어 질문으로 영어 문서를 잘 못 찾음 | 답변 품질 저하 | 1주차에 먼저 시험. 알람 번호는 정확 조회. 필요하면 질문을 영어로 바꿔 검색 |
| 2 | 비서가 문서에 없는 숫자·절차를 말함 | 안전 문제 | 찾은 조각만으로 답, 출처 없는 답은 표시 안 함, 안전 절차는 고정 서식 |
| 3 | 구형 제어기 문서가 섞여 틀린 알람 안내 | 신뢰 저하 | 문서 조각마다 제어기 세대 표시, 알람 질문은 NGC만 |
| 4 | 알림이 너무 많음 | 아무도 안 봄 | 중요도 3단계, 반복 알람 묶기 (4.3) |
| 5 | (안 B) 잘못된 자동 처리 | 기록 오류, 책임 문제 | 되돌리기 쉬운 일만 자동, 처리 기록과 되돌리기 버튼 |
| 6 | 가상 데이터가 비현실적 | 시연 설득력 저하 | 실제 공개 기록 모양을 따르고 자동 점검 ([설계서 9장](가상데이터설계서_v1.md#9-만든-데이터-점검-기준)) |
| 7 | 3주에 기능이 많음 | 미완성 | 필수 7개 먼저. 권장은 줄이는 순서를 미리 정함 (12.2) |
| 8 | 문서 저작권 | 공개 불가 | 내부 시연용, 공개 저장소에 원문을 올리지 않음 |

## 15. 심사 대비

실제 심사 기준을 모르는 상태에서, 일반적인 기준으로 예상한 것이다.

### 15.1 기준별 예상

| 기준 | 예상 | 이유 | 점수를 올리는 방법 |
|---|---|---|---|
| 주제 적합성 | 상 | 실제 설비, 실제 공정 구조, 제조 운영 표준(ISA-95) | — |
| 근거 신뢰성 | **상** | 공식 알람 865개, KOSHA 지침, 출처 표시 | 시연 중 출처를 눌러 원문을 보여 준다 |
| 실용성 | 중상 → 상 | 인력 격차·고령화, 정비 중 끼임 사망 61% 등 정부 통계로 문제가 뒷받침됨 (3.1) | 현장 통계를 발표 앞부분에. 가능하면 현장 인터뷰 1건 |
| 독창성 | 중 → 중상 | 매뉴얼 질문 답변, 교대 인수인계 요약은 이미 상용 제품에 있음 (6.2) | 안전 절차 강제, 공식 문서 인용, 한국어·국내 법령, 한 흐름 연결을 강조. 가장 가까운 사례를 먼저 밝히고 차이를 보여 줌 |
| 구현 범위·완성도 | 중~중상 | 3주에 기능이 많음 | 반쯤 된 기능 13개보다 **끝까지 되는 흐름 하나** |
| AI 활용의 적절성 | 중상 | 계산은 코드, 문장은 AI, 안전은 고정 서식으로 역할 구분 | 답변 정확도를 숫자로 제시 |
| 데이터 | 중 | 운영 데이터가 가상 | 가상 데이터 설계서와 점검 결과, 실제 데이터로 학습한 공구 모델 |
| 발표·시연 | 중상 | 알람 하나로 이어지는 3분 흐름 | 실시간 시연 실패 대비 녹화본 준비 |

**예상 종합: 중상.** 아래 세 가지를 갖추면 상까지 가능하다고 본다.
1. 비서 답변 정확도 숫자 (예: 평가 질문 50개 중 정답 수, 출처 일치율)
2. 국내 현장 통계 (3.1에 확보함). 기사로만 확인한 숫자는 원문으로 다시 확인
3. 시연 흐름을 끝까지 실패 없이

### 15.2 안 A / 안 B에 따른 차이

| 구분 | 안 A | 안 B |
|---|---|---|
| 독창성 | 중상 | 상 가능 |
| 완성도 위험 | 낮음 | 중간 |
| 예상 질문 | "그냥 챗봇과 뭐가 달라요?" → 먼저 알리기·브리핑으로 답 | "잘못 자동 처리하면요?" → 처리 기록·되돌리기로 답 |

### 15.3 예상 질문과 답변 방향

| 예상 질문 | 답변 방향 |
|---|---|
| 데이터가 가짜 아닌가요? | 운영 기록은 가상이 맞다. 알람·정비 항목·안전 절차는 실제 문서 그대로이고, 숫자의 크기는 실제 공개 기록에 맞췄다 |
| AI가 틀린 말을 하면요? | 찾은 문서로만 답하고 출처를 붙인다. 안전 절차는 AI가 아닌 고정 서식이다. 정확도는 평가 질문으로 측정했다 |
| 실제 설비에 붙일 수 있나요? | Haas 공식 데이터 수집 방식(MTConnect 포트 8082, Q 명령)에 맞춘 항목 이름을 쓴다 |
| 왜 설비를 자동으로 조작하지 않나요? | 정비 중 설비가 움직이지 않게 하는 것이 법 제92조와 잠금·표지 지침의 핵심이기 때문이다 |
| 기존 제품과 뭐가 다른가요? | MachineMetrics Max AI가 가장 가깝다고 먼저 밝힌다. 차이는 잠금·표지 강제, 공식 문서 인용, 작업지시서까지 이어지는 흐름, 한국어·국내 법령 (6.2) |

## 16. 기획서로 충분한가

### 16.1 기획서 항목별

| 기획서 항목 | 자료 상태 | 판단 | 남은 부족함 |
|---|---|---|---|
| 주제·배경 | 설비·문서 근거 + 현장 통계(3.1) | **충분** | — |
| 공정 흐름 | 순서는 가상, 구조는 실제 기록으로 확인, 가상 사내 문서로 공정별 내용 보완 | 충분 | 자동차 브래킷 실제 공정 자료 없음 → "가상 공정" 표시 |
| 비서 기능 (AST) | 데이터와 계산식 있음 | 충분 | 브리핑 형식은 팀 설계 |
| 정비 기능 (MNT) | 알람·안내·정비 일정·안전 지침 모두 실제 | **충분** | 한국어 검색 성능은 아직 시험 안 함 |

| 품질 기능 (QLT) | 규칙은 실제, 도면 값은 가상 사내 문서 | 보통 | 실제 부품 도면 없음 |

| 개발 환경·구조 | 일반적인 웹 구조 | 충분 | 기술 선택 팀 확정 |

### 16.2 결론

- **이 주제로 기획서를 쓰는 것은 가능하다.** 정비 영역(알람 → 카드 → 작업지시서 → 이력)은 거의 모든 내용이 실제 문서로 뒷받침되고, 현장 문제(인력 격차, 정비 중 사고)도 정부 통계로 뒷받침된다.
- 기획서에서 **"가상"이라고 밝혀야 하는 것**: 공정 순서, 운영 데이터, 부품 도면 값, 알람 심각도, 경고 기준값, 가상 사내 문서.
- **"가정"이라고 밝혀야 하는 것**: "매뉴얼이 흩어져 있다", "알람 대응을 경험에 의존한다". 가능하면 실제 가공 공장 1곳이라도 인터뷰해서 확인한다.
- 남은 일: 기사로만 확인한 숫자(3.1의 4, 5, 7번)를 원문으로 다시 확인한다.

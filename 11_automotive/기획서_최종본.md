## 1. 주제 설명

### 1.1 한 줄 정의

> 알루미늄 엔진 마운트 브래킷을 깎는 가공 라인에서, **AI 운영 비서**가 생산과 설비를 지켜보다가 문제가 생기면 **"무엇이 문제인지 → 생산에 어떤 영향이 있는지 → 어떻게 안전하게 조치하는지"** 를 근거와 함께 먼저 알려 주고, 작업지시서·작업기록서·교대 보고서·일일 보고서의 초안까지 써 주는 플랫폼.

### 1.2 실시간 대시보드와 무엇이 다른가

대시보드는 화면 하나일 뿐이다. 중심은 **"사건이 생기면 비서가 다음 일을 이어서 준비하는 흐름"** 이다.

| 구분 | 실시간 대시보드 | 이 플랫폼 |
|---|---|---|
| 보여 주는 것 | 지금 상태, 숫자, 차트 | 지금 상태 + **생산 영향 + 해야 할 일과 방법** |
| 알람이 뜨면 | 빨간색으로 바뀜 | 지침카드, 생산 손실, 안전 절차, 작업지시서 초안, 의심 로트 표시까지 이어짐 |
| 사람이 할 일 | 화면을 보고 스스로 판단 | 비서가 정리한 것을 확인·수정·확정하고 현장 작업 |
| 시간 | 지금 | 지금 + 지난 교대 + 오늘 목표 + 앞으로의 일정 |

### 1.3 운영 관리 플랫폼(MOM)이란

국제 표준(ISA-95)은 공장 운영을 네 영역으로 나눈다. 이 플랫폼은 **생산과 정비를 중심**으로 하고, 품질과 재고는 가볍게 다룬다.

| 영역 | 하는 일 | 이 플랫폼에서 |
|---|---|---|
| 생산 | 가동 현황, 목표 대비 실적, 작업지시, 로트 추적 | **중심** |
| 정비 | 고장 대응, 예방 정비, 작업기록, 공구 관리 | **중심** |
| 품질 | 검사, 불량 관리 | 검사 기록·불량 집계 (권장) |
| 재고 | 공구, 소모품, 원자재, **완제품** | 수량·사용·부족 알림·**출하 기록** (권장). 주문 접수·구매·ERP 연동은 하지 않음 |

| 구분 | 무엇 | 따르는 기준 |

- 단위: Haas 문서의 압력 단위 psi는 그대로 두고 **bar를 괄호로 함께 적는다** (1 bar ≈ 14.5 psi). 예: 100 psi (약 6.9 bar).

- 설비·물체마다의 좌표(가운데 X·Y, 크기, 클릭 확대 때 카메라가 바라볼 점)는 조사 파일 **7장 "3D 배치 기준표"를 그대로** 쓴다 (설계서 5.1, 논리 ERD `plant_layout`·`layout_object`·`equipment_part_shape`).

## 3. 사용자와 현장 문제

### 3.1 현장 문제 (근거 자료)

**주 대상: 자동차 부품을 깎는 중소 규모 협력사 (절삭가공 뿌리기업).** 파일: `docs/background/`

| # | 현장 문제 | 숫자 | 출처 | 확인 수준 |
|---|---|---|---|---|
| 1 | 절삭가공은 법으로 정한 뿌리기술이다 | 2021.12 시행령 개정으로 뿌리기술 6대 → 14대. "정밀가공 부문 ①절삭가공" 추가 | 산업통상자원부 보도자료 (2021.12) | 원문 확인 |
| 2 | 작은 회사일수록 기술 인력을 구하기 어렵다 | 부족률 중소 3.0%, 중견 1.1%, 대규모 0.5%. 부족 인원 39,834명 중 **90.5%가 중소 규모** | 산업통상자원부·KIAT, 2025년 산업기술인력 수급 실태조사 | 원문 확인 |
| 3 | 중소기업 기술 인력이 더 빨리 늙는다 | 50대 이상 비중: 중소 19.5%, 중견 18.1%, 대규모 9.4% | 같은 조사 | 원문 확인 |
| 4 | 설비 데이터 활용이 초기 단계다 | 공장 보유 중소·중견 기업의 스마트공장 도입 19.5%, 도입 공장의 75.5%가 기초 단계, 도입 기업의 주요 기술 중 MES 14.4%, 전체 기업 중 제조 AI 도입 0.1% | 중소벤처기업부·스마트제조혁신추진단, 제1차 스마트제조혁신 실태조사 보도자료 (2025.4.28, 2023년 기준) 1·3쪽 | 원문 확인 |
| 5 | 자동차 1차 협력사가 줄었다 | 2019년 824곳 → 2023년 691곳 (2024년 685곳, 2025년 701곳) | 한국자동차산업협동조합 누리집 '부품산업현황 > 기업현황' (연도별 화면) | 원문 확인 |
| 6 | 끼임 사망이 늘었다 | 2024년 끼임 사망 66명, 전년보다 22.2% 증가 | 고용노동부 (2025.3) | 원문 확인 |
| 7 | **끼임 사망의 대부분은 정비·청소 같은 비정형 작업 중에 일어난다** | 제조업 끼임 사망자 374명 중 229명(61.2%)이 청소·점검·조정·정비·수리·교체 등 비정형 작업 중 (2016~2020) | 고용노동부·안전보건공단 보도자료 「제8차 현장점검의 날」 (2021.10.27) 1·3쪽 | 원문 확인 |
| 8 | 숙련 인력이 빠지면 복구가 느려진다 | 정지 후 복구 시간 49분 → 81분. 대형 자동차 공장 정지 비용 시간당 230만 달러 | Siemens, True Cost of Downtime 2024 (**해외 대기업 기준**) | 원문 확인 |

- "심각한 인력난"보다 **"규모별 격차와 고령화"** 로 쓰는 것이 정확하다 (부족률 자체는 2~3%로 몇 년째 비슷).
- 4, 5, 7번 원문은 `docs/background/원문/`에 있다 (2026-10-05 확인). 4번의 MES 14.4%는 "스마트공장을 도입한 기업" 안의 비율이고, 7번 단위는 사망자 수(명)다.
- 5번은 2025년에 701곳으로 다시 늘었다. 2019년 집계에는 2020년 문을 닫은 버스 회사가 들어 있어 2019년과 이후 숫자를 그대로 비교하기 어렵다. 발표에서는 "5년 사이 줄었다" 정도로만 쓰고 수치의 추세를 과장하지 않는다.
- 현장 인터뷰를 대신해 **문헌으로 두 가정을 확인했다** (2026-10-05, `docs/background/현장가정_근거/`).

| 가정 | 확인 결과 | 근거 |
|---|---|---|
| A. 매뉴얼이 흩어져 있어 찾기 어렵다 | **간접 근거.** "영어로 되어 있다"는 근거가 없어 주장하지 않는다 | 국내 CNC는 95% 이상이 외산(헤럴드경제 2025.6, 산업부 발표 기사). 컨트롤러마다 "수천 쪽씩 되는 매뉴얼 가이드북"(대한산업공학회지 2025, 201쪽). 팀이 모은 자료도 조작·알람 매뉴얼은 한국어판이 있지만 정비 문서와 일부 알람 문서는 영문뿐이다 |
| B. 알람 대응을 숙련자 경험에 의존한다 | **직접 근거** (연구의 배경 설명 수준) | "두꺼운 매뉴얼 가이드북을 찾아보거나 그동안 쌓은 노하우를 기반으로 해결… 휴먼 에러가 발생할 수 있다"(대한산업공학회지 2025, 201쪽, CNC 알람 대상), "CNC 고장 진단은 경험 많은 엔지니어에 의존"(Liu 외, *Engineering* 2025), 뿌리산업 고령화로 숙련 전수 단절 위험(파이낸셜뉴스 2022.8, 아주경제 2026.2) |

- 발표 문장: "CNC 알람 대응은 매뉴얼 검색과 숙련자 노하우에 의존한다는 연구가 있고, 고령화로 그 노하우가 끊길 위험이 지적됩니다." 국내 중소 절삭 현장의 설문 수치는 없으므로 "몇 %가 그렇다"고는 말하지 않는다.

**문제 정의**

> 자동차 부품 절삭가공은 법으로 정한 뿌리기술이고, 이 일을 하는 중소 협력사는 기술 인력을 구하기 어렵고 인력도 더 빨리 늙고 있다. 설비 데이터와 AI 활용은 아직 초기 단계다. 그런데 제조업 끼임 사망의 약 60%가 정비·청소 중에 일어난다. 그래서 **숙련자가 없어도 생산 상황을 파악하고, 알람에 올바르고 안전하게 대응하고, 그 기록을 빠짐없이 남기도록 돕는 도구**가 필요하다.

## 4. AI 운영 비서

### 4.1 비서가 하는 다섯 가지 일

| # | 하는 일 | 언제 | 예시 |
|---|---|---|---|
| ① | **먼저 알리기** | 사건, 기한, 목표·재고 이상 | "VF2-01에서 992 알람. 충돌 의심입니다" / "이 속도면 교대 목표보다 12개 부족합니다" / "M6 탭 재고가 안전 재고 아래입니다" |
| ② | **반복 알람 감지 (2단계)** | 1단계: 같은 알람이 되풀이될 때 / 2단계: 조치 계획을 쓴 뒤에도 다시 날 때 | 1단계: "VF2-02의 2075 알람이 이번 주 세 번째입니다. 지난 두 번의 조치: 윤활유 보충(작업기록 MR-0912, MR-0918). 근거: 고장 대응 매뉴얼 DOC-03 §2.11" / 2단계: "조치 계획을 쓴 뒤에도 2075가 다시 났습니다(지난 조치 효과 없음). 원인 점검 작업지시서 AI비서 초안을 만들었습니다" (9장 AST-02) |
| ③ | **브리핑** | 교대 시작 | 지난 교대 요약, 오늘 목표, 진행 중 로트, 그리고 **먼저 챙길 일 전부**(잠금·표지 중인 설비, 미해결 알람, 반복 알람, 병목, 예방 정비 기한, 교체할 공구, 재고 부족 등)를 정해진 순서로 (4.3) |
| ④ | **문서 초안 쓰기** | 알람, 작업 완료, 교대 끝(17:00·05:00), 하루 끝(다음 날 06:00) | 작업지시서, 작업기록서, 교대 보고서, 일일 보고서의 "AI비서 초안" |
| ⑤ | **답하고 덧붙이기** | 물을 때 | 답 + 출처 + 관련 정보 ("이 알람은 이번 주 두 번째입니다") |

### 4.2 비서가 답할 수 있는 질문

| 질문 종류 | 예시 | 답의 재료 | 방식 |
|---|---|---|---|
| 문서 질문 | "992 뜨면 뭐부터 봐?" "공기 압력 정상 범위는?" "쿨런트가 뭐야?" | **가상 사내 문서 세트 DOC-01~07 + 용어집** (10장) | 문서 검색 → 답 + 사내 문서 출처 (문서 이름·번호·§절). 예: "쿨런트가 뭐야?" → 용어집 §5 근거로 "절삭유" |
| 운영 질문 | "어제 야간에 VF2-01 몇 번 멈췄어?" "LOT-2609-041-1 검사 결과는?" | 운영 DB | **정해진 조회 도구**를 비서가 골라 씀 |
| 섞인 질문 | "2075가 왜 자꾸 떠?" | 작업기록 + 정비 일정 + 문서 | 조회 도구 + 문서 검색 |

- 비서가 SQL을 직접 쓰지 않는다. 미리 만든 조회 도구 10여 개(설비 상태, 알람, 지표(MTTR·MTBF 포함), 생산 실적, 로트, 작업지시, 작업기록, 예방 정비 기한, 공구 수명, 재고·출하, 센서 추세, 설비 사양) 중에서 골라 쓴다. 도구 호출의 입력·출력은 **정해진 JSON 칸**으로 주고받는다 (12.2).
- **출처 표시 (2026-10-06 결정):** 답·지침카드·문서 초안·화면 어디에도 **원문 출처를 표시하지 않는다.** 출처는 "고장 대응 매뉴얼 DOC-03 §2.1", "용어집 §4"처럼 **사내 문서 이름 + 문서 번호 + §절**만 쓴다. 사내 문서는 쪽이 없는 문서라 쪽 번호(예: "DOC-01:7p")는 쓰지 않는다. 원문 근거는 사내 문서 **본문 안**의 [실제]/[참고] 표시와 원문 대응표에 남아 있어 사람이 따라갈 수 있다 (비서는 인용하지 않음).
- **출처 눌러 보기:** 출처 글씨에 마우스를 올리면 작은 요약 카드(문서 이름, 문서 번호·개정, 절 제목, 그 절 앞부분 2~3줄)가 뜨고, 클릭하면 그 사내 문서가 **팝업 창**으로 열려 그 절로 이동·강조된다. 터치 화면은 탭 = 요약 카드, 카드의 [문서 열기] = 팝업 (호버에만 기대는 정보 없음).

### 4.3 알림 규칙

| 중요도 | 예시 | 보내는 방식 |
|---|---|---|
| 긴급 | 정지 등급 알람 | 화면 팝업 + 소리, 해당 설비 작업자·보전 담당자 |
| 주의 | 주의 등급 알람, 반복 알람(1·2단계)·원인 점검 요청, 병목 발생·이동, 목표 미달 위험, 로트 납기 지연 위험, 관리도 이상, 재고 부족, 기한 넘긴 예방 정비, 공구 수명 90%, 승인 대기 2시간, CMM 알림 3종(판정 불일치·결과 파일 오류·결과 미수신) | 알림 목록 + 브리핑에 포함 |
| 참고 | 조작 안내 알람, 예방 정비 하루 전, 승인 대기 30분, 교대 보고서 확정 요청, 문서 수정 알림 | 알림 목록, 브리핑·보고서 |

- 같은 알람이 **1분 안에 3번 이상** 반복되면 하나로 묶는다.
- **알림 폭주:** 10분에 10건이 넘으면 묶어서 "폭주"로 표시하고, 10분에 5건 아래로 내려가면 푼다. 평소 목표는 운전원 1명당 긴급+주의 **10분에 1건 미만**, 중요도 비율은 긴급 약 5%·주의 약 15%·참고 약 80% [참고: EEMUA 191 요약, IChemE 알람 합리화 자료].
- 24시간 넘게 처리 안 된 주의 알림은 브리핑에서 **잠금·표지 중인 설비 바로 다음**(아래 순위 0-1)에 올린다.
- 알릴지 말지와 **보고 순서**는 **규칙**이 정하고, 비서는 알림 문장과 "관련 정보 한 줄"만 붙인다.

**"전부 보고" 순서 (2026-10-06 결정, 사내 문서 DOC-07 §10.5)** — 비서가 몇 개만 골라 보고하지 않는다. **프로그램이 정해진 목록·기준으로 문제를 전부 모으고, 아래 순서로 정렬**한다. 비서는 그 순서대로 문장만 쓴다. 교대 시작 브리핑 "먼저 챙길 일", 일일 보고서 "오늘의 문제", 교대 보고서 인계 사항에 쓴다.

| 순위 | 이름 | 들어가는 것 | 같은 순위 안 정렬 | 접기 |
|---|---|---|---|---|
| **0** | 안전 | 잠금·표지 중인 설비 | 잠금 시작 시각 이른 순 | 접지 않음. 없으면 "잠금·표지 중인 설비 없음" |
| 0-1 | 오래 방치 | 24시간 넘게 처리 안 된 주의 알림 | 처리 안 된 시간 긴 순 | 접지 않음 |
| **1** | 긴급 | 처리 안 된 정지 등급 알람, 지금 DOWN인 설비 | 지금 멈춰 있는 것 → 정지 시간 긴 순 → 같으면 병목 공정(OP-30) 먼저 | 접지 않음 |
| **2** | 생산 위험 | 목표 미달 위험, 병목 발생·이동(재공 20개 초과 포함), 로트 납기 지연 위험 | 목표 미달(부족 수량 큰 순) → 병목(속도 손실 수량 큰 순) → 납기(납기 이른 순) | 자세한 내용만 접음 |
| **3** | 주의 | ① 반복 알람 2단계 → 1단계 ② 처리 안 된 주의 등급 알람 ③ 품질(관리도 이상, 보류·강화 로트, 의심 로트 제안, CMM 알림 3종) ④ 공구 수명 90% 이상, 예방 정비 기한 넘김, 재고 부족 ⑤ 승인 대기 2시간 이상 | 묶음은 ①~⑤ 순서. 묶음 안: 반복 알람 = 횟수 많은 순 / 공구 = 사용률 높은 순 / 정비 = 넘긴 일수 많은 순 / 재고 = (재고 ÷ 안전 재고) 작은 순 / 승인 = 대기 시간 긴 순 | 자세한 내용만 접음 |
| **4** | 참고 | 조작 안내 알람, 예방 정비 하루 전, 승인 대기 30분, 교대 보고서 확정 요청, 문서 수정 알림 | 발생 시각 이른 순 | 자세한 내용은 기본으로 접음 |

- 화면 머리에 **"전체 N건 (안전 a · 긴급 b · 생산 c · 주의 d · 참고 e)"** 을 항상 보인다. 건수가 0인 순위도 이름과 "-"를 보인다 (순위 0은 "잠금·표지 중인 설비 없음"). 0-1 오래 방치는 주의 알림이라 "주의" 건수에 센다. **개수를 잘라서 보여 주지 않는다** — 항목마다 한 줄은 항상 보이고, 자세한 내용만 접을 수 있다. 예외는 현장 보기 알람 띠 하나다: 넘치면 마지막 줄을 "외 N건"으로 줄이되 머리의 N은 전체 수이고 누르면 전부 펼친다.
- 같은 설비·같은 원인은 한 줄로 묶는다 (예: 2075 반복 알람 + 축 윤활유 점검 기한 넘김 + 축 윤활유 재고 부족 → 한 줄, 높은 순위 쪽). 묶인 줄은 1건으로 센다 (머리의 N = 화면 줄 수). 위 정렬이 같으면 발생 시각 이른 순.
- 순서는 프로그램이 정하고 **비서는 순서를 바꾸거나 항목을 빼지 않는다.**
- 근거 [참고]: ISA-18.2 우선순위 틀(결과 심각도 × 대응 가능 시간, Rockwell 백서), HSE CHIS6, 교대 인수인계 체크리스트 실험(ASM 컨소시엄 2011, "빠지면 안 되는 항목", "보고할 것 없음" 표시), 잠금·표지 인계 맨 위(DOC-05 §2.3) — `docs/production/운영기준_근거/병목조치_반복알람_우선순위_조사.md` 4장. 순위 2를 3보다 위에 둔 것과 묶음 순서는 [제안].

### 4.4 비서의 행동 범위 (확정: 문서 작성만 자동)

| 등급 | 기준 | 하는 일 |
|---|---|---|
| **자동** | 기록·책임에 영향이 없음 | 알림, 지침카드, 브리핑, 지표·손실 계산 |
| **AI비서 초안 + 사람 확정** | 문서로 남지만 사람이 고칠 수 있음 | 작업지시서, 작업기록서, 교대 보고서, 일일 보고서, 정지 사유 추천 |
| **사람만** (비서는 제안까지) | 책임이 따르거나 안전과 관련 | 작업지시서 승인, 담당자 지정, 정지 사유 확정, 로트 보류·해제, 출하 확정, 병목 조치(투입 조절·정비 일정 변경 등), 설비 조작, 잠금·표지, 정비 |

나누는 기준은 세 가지다: **되돌릴 수 있나 / 책임자가 필요한가 / 안전과 관련 있나.**

### 4.5 AI비서 초안과 수정 이력

```
AI비서 초안 (v0) ──▶ 사람 수정 (v1, v2 …) ──▶ 확정 (잠김) ──▶ (필요시) 확정 후 수정: 새 버전 + 사유 필수
```

- 모든 문서(작업지시서, 작업기록서·간이 기록, 교대 보고서, 일일 보고서, 사내 문서, 예방 정비 실시 기록, 출하 기록 — **7종**, AST-03)에 **버전, 수정한 사람, 시각, 바뀐 내용(전·후), 사유**가 남는다. AI가 쓴 부분과 사람이 고친 부분을 구분할 수 있다.
- 수정 알림: 작업지시서가 고쳐지면 → 담당 보전원 / 보고서가 고쳐지면 → 관리자 / 사내 문서가 개정되면 → 관련 역할 전체.

### 5.2 알람 등급별 흐름

| 알람 등급 | 흐름 | 예 |

| 주의 | 지침카드 + **간이 작업기록** (작업자가 조치를 고르고 확정) | 2075 축 윤활유 저장소 비워짐 |

## 6. 생산을 보여 주는 방법

v2는 "고장"에 치우쳐 있었다. v3는 **같은 데이터를 생산 관점으로 다시 보여 주는 방법** 다섯 가지를 모두 넣는다.

| # | 방법 | 화면·기능 | 계산 |
|---|---|---|---|
| ① | **목표 대비 실적** | **총 목표**(교대 목표 90 + 이월) vs 현재 실적 "지금 N / 총 목표 N개", 시간대별 실적 그래프(총 목표선·예측 점선), "이 속도면 목표보다 N개 부족" 예측 | 예측 = 현재 실적 + (최근 1시간 속도 × 남은 시간) |
| ② | **고장을 생산 손실로 환산** | 정지 1건마다 "약 7개 손실". 교대·일일 보고서에도 표시 | 손실 수량 = 정지 시간 ÷ 그 설비의 기준 사이클 시간 (추정치로 표시) |
| ③ | **공정 사이 재공·병목** | 2D 라인의 공정 사이에 쌓인 부품 수. 기준을 넘으면 주황. 지금의 병목 공정 표시, **병목 위치가 바뀌면 표시가 따라 옮겨 감** | 재공 = 앞 공정 완료 수 − 다음 공정 투입 수. 병목 판단은 6.1 |
| ④ | **생산 알림** | 목표 미달 위험, 로트 납기 지연 위험 | ①의 예측과 로트 납기 비교 |
| ⑤ | **로트 추적** | 원자재 로트 → 생산 로트 → 공정별 실적·알람·공구 → 검사 → 보류·**출하(출하 번호·출하처)** | 작업지시를 교대마다 나눈 생산 로트 (PRD-05), 출하 기록 (INV-01) |

### 6.1 고장과 병목은 다르다

설비가 멈추지 않아도 **한 공정이 느려지면** 앞에는 부품이 쌓이고 뒤는 기다린다. 이것이 병목이다. 고장과 병목을 따로 보여 줘야 "어디 때문에 목표를 못 채우는지"를 정확히 알 수 있다.

| 구분 | 고장 | 병목 |
|---|---|---|
| 무엇 | 설비가 알람으로 멈춤 | 설비는 돌지만 한 공정이 라인 전체 속도를 정함 |
| 보이는 모습 | 설비 빨강 (DOWN) | 앞 재공 증가, 앞 공정 "막힘", 뒤 공정 "앞 공정 대기" |
| 손실 이름 | **고장 손실** (정지 시간) | **속도 손실** (OEE의 성능 손실) |
| 비서가 하는 일 | 지침카드, 작업지시서 초안 | 병목 알림 + 원인 + 목표 영향 + **원인별 조치 제안** (아래 표) |

**고장이 아닌 병목 원인 4가지** (데이터에 모두 넣는다, [설계서 5.18](가상데이터설계서_최종본.md#518-병목-상황-고장이-아닌-원인))

| # | 원인 | 병목 위치 |
|---|---|---|
| ① | 사이클 시간 증가 (공구 마모, 이송을 낮춤) | OP-30이 더 심해짐 |
| ② | 설비 1대만 가동 (VF2-02 예방 정비, 긴 셋업) | OP-30 (속도 절반) |
| ③ | 검사 강화 (의심 로트를 발췌 → **전수** + 측정 항목 확대) | **OP-50으로 옮겨 감** |
| ④ | 묶음 대기 (OP-40은 30개가 모여야 세척) | OP-30→40 사이에 잠깐 쌓임 |

**병목 판단 규칙** [가상, 팀 규칙 — DOC-07에 적음]: 최근 30분 동안 **바로 앞 재공이 늘고, 앞 공정이 "막힘"이거나 뒤 공정이 "앞 공정 대기"** 인 공정을 병목으로 본다 (설계서 5.18과 같음). 판단은 코드가 하고, 비서는 원인과 영향을 문장으로 옮긴다.
- 근거 [참고]: 설비가 쉬지 않고 일한 시간이 가장 긴 공정을 병목으로 보는 "active period" 방법 (Roser 외, Winter Simulation Conference 2001·2002), 막힘(blocking)·굶음(starvation) 개념 (MIT 2.854 강의) — `docs/production/병목_재공/`

**병목 원인별 조치** (2026-10-06 결정, 사내 문서 **DOC-07 §7.5**) — 병목 발생·이동 알림에 해당 원인의 조치 줄을 관련 정보로 붙인다. **조치는 사람(SUP 등)이 하고 비서는 제안만** 한다 (4.4).

| 원인 | 비서가 제안하는 조치 | 누가 결정·실행 | 따를 사내 문서 |
|---|---|---|---|
| ① 사이클 시간 증가 (공구 마모) | 공구 수명 확인 → 90% 이상이면 사이클 끝난 뒤 교체, 80~90%이면 앞당겨 교체할지 검토, 교체 뒤 **초품 검사**, 90% 넘긴 뒤 가공 로트는 의심 로트 검토 | OPR·MNT 교체, SUP 판단 | DOC-01 7.2·7.3, DOC-06 3.1·4.2 |

| ③ 검사 강화 (OP-50으로 병목 이동) | 보류 로트 **판정을 결과 나오는 대로** 진행, 강화 범위 확인(원인이 공구이고 교체 기록이 있으면 다음 1개, 아니면 2개), 보통 검사로 돌아갈 조건 안내 | SUP (판정·범위), MGR (폐기 승인) | DOC-06 3.3·4.1·4.2·6.1 |

| 고장 (설비 DOWN) | 지침카드·DOC-03 점검 순서, **병목 공정(OP-30) 고장은 수리 우선순위를 높게** 제안, 복구 뒤 초품 검사·의심 로트 검토 | MNT 수리, SUP 지정·승인 | DOC-02 §2, DOC-03, DOC-05 §2, DOC-06 |

## 7. 목적과 차별성

### 7.1 목적

| # | 목적 | 시연에서 확인하는 방법 |
|---|---|---|
| 1 | 알람부터 첫 조치까지의 시간을 줄인다 | 알람 → 지침카드가 몇 초 안에 뜨는 것 |
| 2 | 고장과 병목의 **생산 영향**을 바로 보이게 한다 | 정지 → 고장 손실, 의심 로트 표시 / 병목 → 재공 증가, 속도 손실, 병목 위치 이동 / 둘 다 → 목표 미달 예측 |
| 3 | 정비를 **안전 절차와 함께** 표준화한다 | 작업지시서에 잠금·표지(작업 전 6단계 + 해제 3단계)가 빠짐없이 들어가는 것 |
| 4 | 사람이 쓰던 문서를 비서가 초안으로 쓴다 | 작업지시서·작업기록서·교대·일일 보고서의 AI비서 초안과 수정 이력 |
| 5 | 기록을 숫자로 남긴다 | 작업기록서 확정 → MTTR·정지 원인·재고가 바뀌는 것 |

### 7.2 효율과 비용은 이렇게 보여 준다

| 항목 | 방법 |
|---|---|
| 효율 | 시연에서 **직접 잰다.** ① 알람 → 지침카드 표시 시간 ② 보고서·작업지시서 작성 시간: 팀원이 손으로 쓴 시간 vs AI비서 초안을 확인·확정한 시간 |
| 비용 | 국내 중소 공장의 정지 비용 근거가 없다. 그래서 **금액이 아니라 손실 수량(개)** 으로 보여 준다. Siemens 정지 비용은 "해외 대기업 기준"이라고 밝히고 배경으로만 쓴다 |

### 7.3 비슷한 제품·연구 (2026-10-02 조사, `docs/related/`)

**이미 흔한 것 — 차별점이 아니다**

| 기능 | 이미 하는 곳 |
|---|---|
| 매뉴얼 질문 답변·고장 진단 | MaintainX, Tulip, Cognite, Aquant, MachineMetrics |
| 매뉴얼로 작업지시서 초안 | MaintainX, Cognite |
| CNC 가동률·정지·알람 모니터링, 생산 실적 | MachineMetrics, Datanomix, HaasConnect, Mazak SmartBox |
| AI 교대 인수인계 요약 | MachineMetrics Shift Handover (2026.4) |
| CNC 알람을 매뉴얼로 해석하는 연구 | Park 외, PHM Asia-Pacific 2025 / Liu 외, *Engineering* 2025 |

**가장 가까운 제품: MachineMetrics Max AI**

| 항목 | MachineMetrics Max AI | 이 플랫폼 |
|---|---|---|
| 대상 | CNC 공장 (미국) | CNC 라인 (한국) |
| 알람 대응 근거 | 과거 발생·조치, 사용자가 올린 사내 문서 | **공식 제조사 문서로 만든 사내 문서 세트** (답에는 사내 문서 번호·절, 사내 문서 본문에는 항목마다 원문 근거) |
| 교대 인수인계 | 있음 | 있음 (교대 보고서 + 브리핑) |
| 문서 작성 | **만들지 않음** ("Max는 대신 행동하지 않는다") | 작업지시서·작업기록서·교대·일일 보고서 **AI비서 초안 + 사람 확정 + 수정 이력** |
| 안전 절차 | 인수인계에서 안전 항목을 먼저 정렬 | **KOSHA 잠금·표지 6+3단계를 고정 서식으로 강제** |
| 언어·법령 | 영어 | 한국어, 국내 법령·KOSHA |

**가장 가까운 연구:** Park 외(2025)는 LLM이 공작기계 매뉴얼로 CNC 알람을 해석해 **설비 조작까지 자동화**하는 연구다. 이 플랫폼은 반대로 설비 조작을 하지 않고, 안전 절차를 강제한다.

### 7.4 이 플랫폼의 차별점

| # | 차별점 | 비교 대상과의 차이 |
|---|---|---|
| 1 | **안전 절차를 AI가 아닌 고정 서식으로 강제** | 다른 제품은 안전 질문에 답하거나 안전 항목을 앞에 정렬하는 정도 |
| 2 | **공식 문서를 근거로 만든 한국어 사내 문서 세트, 답마다 사내 문서 번호·절 출처** (사내 문서 본문에 항목마다 [실제]/[참고] 원문 근거) | 다른 제품은 회사가 올린 문서를 그대로 쓴다 (품질이 회사마다 다름) |
| 3 | **알람 → 카드 → 작업지시서 → 작업기록서 → 보고서가 한 흐름**, 생산 영향까지 연결 | 모니터링, 질문 답변, 작업지시가 서로 다른 제품에 나뉜 경우가 많다 |
| 4 | **문서는 비서가 초안, 사람이 확정, 모든 수정이 이력으로 남음** | Max AI는 문서를 만들지 않는다 |
| 5 | 한국어 + 국내 법령·KOSHA | 조사한 해외 제품은 모두 영어 중심 |

> 발표에서는 "이런 것이 없다"고 말하지 않는다. **"이 조합을 한국어 CNC 라인에 묶은 사례는 이번 조사에서 찾지 못했다"** 고 말하고, MachineMetrics와 Park 외(2025)를 가장 가까운 사례로 먼저 소개한다.

```
                         └─▶ MNT-03 작업지시서 (AI비서 초안 → SUP 승인) ─▶ 정비
                                                                          │
                              MNT-05 작업기록서 (AI비서 초안 → MNT 확정) ◀─┘
                                     │            ├─▶ INV-01 사용 부품 차감
                                     │            └─▶ PRD-06 고장 직전 다시 보기 링크
                                     ▼
              PRD-01 MTTR·정지 원인 갱신 ─▶ PRD-02 교대 보고서 ─▶ AST-01 다음 교대 브리핑
                                                    └─▶ PRD-04 일일 보고서
                     (모든 문서의 수정은 AST-03 수정 이력에 남음)
```

- 로트가 OP-50에서 **합격**하면 합격 수량만큼 완제품 재고로 들어오고(INV-01), SUP가 **출하 기록**을 저장하면 빠진다. 로트 추적(PRD-05)은 원자재 로트 → 생산 로트 → 검사 → 출하까지 이어진다.
- 같은 알람이 7일 안에 3번 나면 반복 알람 1단계, 조치 계획 뒤에도 다시 나면 2단계로 원인 점검이 이어진다 (AST-02).

| 실제 크기 (FR-PRD-01-27) | 설비 6대·주요 부품·공장 전체를 실제 치수(단순 도형)로 그린다. 값은 1.4 "공장 배치와 설비 크기" |
| 현장 보기 (FR-PRD-01-28) | OPR의 기본 첫 화면. 현장 큰 모니터용 (6.2 현장 보기 표) |
| AI | 사용하지 않음. 비서 창에서 "이 차트 설명해 줘"는 가능 |

**설비 상태 코드** [가상, 실제 방식에 맞춤] — 화면 표시는 6.2 상태 색 규칙

| 상태 | 실제 데이터의 어떤 값에 해당하나 |
|---|---|
| RUN 가공 중 | MTConnect ACTIVE, Haas Q500 BUSY |
| IDLE 대기 | READY, Haas IDLE — 앞 공정을 기다리거나 로트가 없음 |
| BLOCKED 막힘 | READY — 뒤 재공이 한도(30개, OP-30→40만 60개)에 차서 부품을 내보낼 수 없음. 플랫폼이 재공으로 판단 |
| SETUP 준비 | 작업자 입력 (로트 교체, 공구 교체, 초품 검사) |
| DOWN 고장 정지 | STOPPED + 정지 등급 알람 |
| MAINT 계획 정비 | 예방 정비 작업 진행 중 |

**지표 계산식** [실제, NIST 논문의 ISO 22400 정리]

| 지표 | 식 |
|---|---|
| 가동률 A | 실제 가공 시간 ÷ 계획 가동 시간 (계획 가동 시간 = 교대 480분 − 그 설비의 예방 정비 시간, ISO 22400 계획 정지 PDOT) |
| 성능 E | 계획 사이클 시간 × 생산 수량 ÷ 실제 가공 시간 |
| 양품률 QBR | (양품 + 재작업 양품) ÷ 생산 수량 |
| OEE | A × E × QBR |
| 라인 OEE | OP-30 2대(VF2-01·02)를 한 작업장으로 보고 시간·수량을 합해 계산 (라인 계획 가동 시간 = 480분 × 2대). 근거: ISO 22400 OEE는 여러 설비 작업장에도 씀, OEE.com "라인 OEE는 제약 공정에서 잰다" [참고] — DOC-07 6.2 |
| MTTR | 수리 시간 합 ÷ 고장 횟수 |
| MTBF | 고장 간격 시간 합 ÷ 고장 횟수 |

**생산 관점 계산** [가상, 팀 정의 — 사내 문서 "설비 데이터·지표 정의서"에 적음]

| 항목 | 식 |
|---|---|
| 교대 실적 | 그 교대에 OP-50을 마친 수량 중 불량이 아닌 것 (양품 + 재작업 양품). ISO 22400 처리율 식과 같음 — DOC-07 4장 |
| 이월·총 목표 | 이월은 **같은 생산일의 주간 → 야간에만**: 야간 이월 = max(0, 90 − 그날 주간 실적). 주간은 늘 이월 0. 하루 목표는 180 고정이고, 야간이 못 채운 수량은 다음 날로 넘기지 않고 **그날 하루 부족**(180 − 하루 실적)으로 남는다. **총 목표 = 교대 목표 + 이월** — 교대 목표를 보이는 모든 화면과 목표 미달 위험에 쓴다. 예: 주간 양품 87 → 야간 총 93개(90 + 이월 3) → 야간 양품 86이면 하루 173 / 180, 그날 7개 부족 (다음 날 주간은 다시 90) [가상] (2026-10-07 팀 UI 검토, DOC-07 §4.1) |
| 교대 목표 | 90개 (이론 최대 480분 ÷ 3.5분/개 ≈ 137개의 약 65%). 65%의 근거 [참고]: 23개 회사 884대 설비의 평균 OEE 65% (Hedman 외 2016, `docs/production/OEE_손실/`) |
| 목표 미달 예측 | 현재 실적 + 최근 1시간 생산 속도 × 남은 시간 |
| 고장 손실 수량 (추정) | 정지 시간 ÷ 해당 설비 기준 사이클 시간 |
| 속도 손실 수량 (추정) | 그 시간의 계획 생산 수 − 실제 생산 수 − 고장 손실 수량 |
| 재공 | 앞 공정 완료 수 − 다음 공정 투입 수 (공정 사이 한도 30개, OP-30→40은 60개) |
| 병목 | 6.1의 판단 규칙 |

- 경고 기준: **가동률 60% 미만(OP-30 설비별)·OEE 59% 미만(OP-30 설비별과 라인 OEE — 병목이 아닌 공정은 막힘·굶음 때문에 늘 낮게 나옴), 30일 MTTR 120분 초과, 재공 20개(약 70분 분량) 초과** — 값과 근거는 [설계서 15장](가상데이터설계서_최종본.md#15-가상-기준값-추천과-근거). 재공 한도는 30개, **OP-30→40만 60개**(30개 묶음 세척 때문).

### PRD-02 교대 보고서 (필수)

| 항목 | 내용 |
|---|---|
| 하는 일 | 교대가 끝나면(**주간 17:00, 야간 05:00**) 그 교대의 인수인계 보고서 AI비서 초안을 만든다. 해당 교대 반장이 고쳐서 확정한다 |
| AI | 숫자는 프로그램이 넣고, 비서는 "특이 사항"과 "다음 교대에 넘길 일" 문장만 쓴다. 문장 속 숫자는 프로그램이 표와 대조한다 |

| 칸 | 내용 | 만드는 쪽 |
|---|---|---|
| 생산 | 총 목표(목표 + 이월) / 실적 / 불량 / 가동률 | 프로그램 |
| 로트 | 이 교대에 만든 로트, 완료·진행·보류 로트 | 프로그램 |
| **필수 정지** | **필수 정지 전부**를 정지 시간이 긴 순서로 (개수 제한 없음). 칸: 설비, 원인, 시간, 손실 수량. 순간 정지(5분 미만)는 건수·합계 시간 한 줄 | 프로그램 |
| 병목 | 병목 공정·원인·시간, 속도 손실 수량, 사람이 고른 조치(원인 번호, 6.1) | 프로그램 |
| 정비 | 작업지시서·작업기록서 번호, 알람, 조치 | 프로그램 |
| 특이 사항 | 3~5문장 | 비서 |
| 인계 사항 | **잠금·표지 중인 설비(맨 위)**, 미해결 알람, 보류·강화 검사 중인 로트, 진행 중 작업지시, 기한 임박 정비, 교체할 공구, 재고 부족 — 빠짐없이, 4.3 "전부 보고" 순서로 | 프로그램 + 비서 문장 |

**필수 정지의 정의** (2026-10-06 결정, 사내 문서 DOC-07 §5.4): 정지 사유가 **고장 그룹(F01~F06)이고 5분 이상**인 정지 전부 (정지 등급 DOWN 전부 + 주의 등급 알람으로 멈춘 정지), 모든 공정. 정렬: 정지 시간 긴 순 → 손실 수량 큰 순 → 시작 이른 순. **소재 대기(M01)는 넣지 않는다** (흐름 정지라 병목 칸). 준비(S 그룹)·계획 정비(P01)도 넣지 않는다. 근거: 5분 경계는 기존 DOC-07 2.2 (고장 정지 로스, ISO 22400·NCS) — 새 숫자를 만들지 않았다.

- **확정 요청과 잠정** (2026-10-07 최종 검토): 교대가 끝나 초안이 생기면 그 교대 반장에게 "교대 보고서 확정 요청"(참고) 알림이 간다. 확정 전에는 그 교대 값을 쓰는 곳(다음 교대 브리핑, 야간 이월, 일일 보고서)이 "잠정"으로 보이고, 확정되면 다시 계산한다.
- 확정 시간: 주간 반장은 퇴근 전에, 야간 반장은 05:00~06:00(일일 보고서 생성 전)에 확정한다. 야간 반장의 이 1시간은 실제로는 연장 근무라 근무 계획에 넣을지 [선택 필요: 팀] (18장).

**양식 근거 [참고]:** NCS 학습모듈 작업계획수립(작업일보 항목: 수량, 실작업 시간, 불량, 손실 시간 원인), 영국 HSE 교대 인수인계 기준(인계할 정보, 점검 질문) — `docs/production/보고서_양식/`

| 항목 | 내용 |
|---|---|
| 하는 일 | 생산일(주간 08:00 ~ 다음 날 야간 05:00)이 끝나면 **다음 날 06:00** [가상]에 하루치 운영 보고서 AI비서 초안을 만든다. 관리자가 확정한다 |

|---|---|
| 하루 생산 | 목표 180(고정) / 실적 / 부족 수량(180 − 실적, 다음 날로 넘기지 않음) / 불량 / OEE(라인 OEE), 교대별 비교 |

### AST-01 교대 시작 브리핑 (필수)

| 항목 | 내용 |
|---|---|
| 하는 일 | 교대가 시작되면 "지난 교대에 무슨 일이 있었고, 이번 교대에 무엇을 챙겨야 하는지"를 보여 준다. 1분 분량이 목표지만 **1분에 맞추려고 항목을 빼지 않는다**. **문서가 아니라 화면**이다 |
| 입력 | 지난 교대 보고서, 오늘 목표, 진행 중 로트·작업지시, 잠금·표지 중인 설비, 미해결 알람, 반복 알람(1·2단계), 병목·목표 미달·납기 위험, 품질(관리도 이상·보류·의심 로트), 예방 정비 기한, 공구 수명 90% 이상, 재고 부족, 승인 대기 문서 |
| AI | 목록과 순서는 **프로그램이 전부 모으고 정한다** (4.3 "전부 보고" 순서). 비서는 그 순서대로 문장만 쓴다. 몇 개만 고르지 않는다 |

| 칸 | 예시 |

**JSON을 쓰는 곳 (2026-10-06 방향 확정)**

| # | 쓰는 곳 | 예 |
|---|---|---|
| ① | 설정 파일 | 라인 구성, 알림 기준값, 교대 시간 |
| ② | 비서 ↔ 프로그램이 주고받는 형식 | 도구 호출 입력·출력, AI비서 초안의 정해진 칸 |

- **운영 데이터 저장은 JSON 파일이 아니라 DB**에 한다.
- 비서 출력은 정해진 JSON 칸으로 받고, 형식이 틀리면 프로그램이 거부하고 다시 요청하거나 기본 문구를 쓴다 [제안] (로컬 LLM은 형식을 틀릴 수 있다).

### 17.2 예상 질문

| 질문 | 답변 방향 |
|---|---|
| 데이터가 가짜 아닌가요? | 운영 기록은 가상이 맞다. 알람·정비 항목·안전 절차는 실제 문서 근거이고, 숫자 크기는 실제 공개 기록에 맞췄다 |
| AI가 틀린 말을 하면요? | 사내 문서·용어집으로만 답하고 사내 문서 번호·절을 출처로 붙인다. 안전 절차는 고정 서식이고, 모든 문서는 사람이 확정한다 |

| 왜 외부 LLM이 아니라 로컬 LLM인가요? | 운영 데이터·사내 문서가 회사 밖으로 나가지 않는다. 대신 한국어 성능·속도는 시험으로 확인하고 위험(16장 11~14)을 관리한다 |
| 비서가 중요한 것만 골라 주면 더 편하지 않나요? | 고르다 빠뜨리는 것이 더 위험하다 (Piper Alpha 사고: 정비 중 밸브 상태가 교대 인수인계에서 빠짐 [참고: ASM 컨소시엄 2011]). 프로그램이 정한 목록·순서로 전부 보여 주고, 화면은 한 줄씩 + 자세한 내용 접기로 읽기 쉽게 한다 (4.3) |
| 그냥 챗봇 아닌가요? | 비서는 먼저 알리고, 문서 초안을 쓰고, 생산 영향을 계산한다. 질문 답변은 다섯 가지 일 중 하나다 |
| 디지털 트윈이라면서 조작이나 시뮬레이션은요? | 디지털 트윈 3단계 중 **모니터링형(디지털 섀도)**까지 구현했다. 설비 조작은 안전 원칙(법 제92조)상 일부러 하지 않는다. 대신 지난 일을 3D로 다시 볼 수 있다 |
| 3D는 보여 주기용 아닌가요? | 숫자는 2D 패널에서 읽고, 3D는 라인 구조와 이상 위치를 한눈에 보는 용도다. 공장과 설비를 실제 크기로 그려 배치를 그대로 보고, 설비를 누르면 그 설비로 확대된다. 정상은 회색이라 이상만 눈에 띈다. 2D 배치도로도 바꿔 볼 수 있다 |
| 왜 설비를 자동으로 조작하지 않나요? | 정비 중 설비가 움직이지 않게 하는 것이 법 제92조와 잠금·표지 지침의 핵심이다 |
| 기존 제품과 뭐가 다른가요? | MachineMetrics Max AI가 가장 가깝다고 먼저 밝히고 7.4의 차이를 말한다 |

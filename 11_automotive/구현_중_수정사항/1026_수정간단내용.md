## 3. 비서 알람 도구가 알람 1건을 두 번 세던 것 고침 (LLM 담당 요청 "필수", DB 담당 처리)

| 항목 | 내용 |
|---|---|
| 왜 | 비서 알람 도구(`assistant.alarms`)가 `alarm_event`를 `equipment_state_log`와 LEFT JOIN한 뒤 `count(*)`로 세서, 상태 기록이 2줄인 알람을 2번 셌다 → 이브 알람 건수가 DB 직접 셈보다 크다(2장 "알아 둘 것") |
| 2줄 생기는 까닭 | 생성기·중계 잘못이 아니라 생성기 규칙이다. WARN·GUIDE 알람의 IDLE 정지는 남은 분 수로 세는데, 근무 밖(쉬는 시간 P02·교대 사이 P03)에는 멈췄다가 다음 근무에 이어 간다(`생성기/gen/flow.py` `_step_machine`). 그래서 알람 1건에 IDLE 2줄이 생기고, 가운데 계획 정지 줄은 알람과 이어지지 않는다. 공용 DB 2건: 알람 9(VF2-01 2075 WARN, 10/2 05:37~05:45 + 09:30~09:40, 사이 06~09시 계획 없음), 알람 52(VF2-01 970 GUIDE, 10/6 12:57~13:00 + 14:00~14:02, 사이 13~14시 휴식). DOWN은 끝 시각이 정해진 정지라 끊기지 않고 알람마다 1줄이다(`ux_state_log_alarm_down`). DB 스키마 주석(`backend/db/schema/50_maintenance.sql`)에도 같은 설명이 있다 |
| 고친 것 | `backend/app/sql/assistant.sql` `alarms`: `count(*)` → `count(DISTINCT a.alarm_event_id)`. `down_min`은 그대로 둠 (DOWN 줄이 알람마다 1줄이라 겹치지 않음, 고치기 전후 값이 같다) |
| 전후 (공용 DB, 읽기 전용) | 10/1~10/25: DB 알람 292 / 전 294 / 후 292. 10/1~지금: 293 / 295 / 293. 어제(10/25): 5 / 5 / 5. 바뀐 줄은 VF2-01 970 GUIDE 15→14, VF2-01 2075 WARN 6→5. `down_min` 합 856.0분(10/1~10/25)·972.0분(지금까지)은 전후 같고 DB 직접 합과 같다 |
| 안 바꾼 것 | 정지 원인 순위(`stop_reasons`)는 정지 구간 단위로 센다. 끊긴 정지가 2회로 보이지만 분 합은 맞고, 교대 보고서 정지 칸과 같은 기준이라 그대로 둔다. 생성기·DB·화면도 그대로 |
| 확인 | 새 시험 `test_alarms_counts_split_idle_once`(시험 DB에서 알람 1건에 IDLE 2줄을 만들고 `times` = 1, 끝나면 되돌림): 고치기 전 쿼리는 `'2' != '1'`로 실패, 고친 뒤 통과. 로컬 Docker DB로 백엔드 시험 전체 100 통과·1 실패(`test_17_staff`: main에서도 같은 실패, 로컬 `mom_test`에 직원 권한이 없음) |
| 서버 반영 | 합친 뒤 AWS 서버에서 `git pull` → `docker compose up -d --build backend` (DB를 되돌리지 않음). `./mom.sh up`·`update`는 하지 않는다 |
| 고친 파일 | `backend/app/sql/assistant.sql`, `backend/tests/test_services_db.py`, `파일설명.md`, 이 파일 |

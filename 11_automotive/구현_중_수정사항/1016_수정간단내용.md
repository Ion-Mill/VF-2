## 1. 외부 Claude AI 비서를 별도 서비스로 붙이기 시작 (`assistant/`)

`261003_창민/claude_bundle_20261016`(비서 백엔드 묶음, 파일 319개)을 `11_automotive/assistant/`에 그대로 복사했다.
기존 `backend/`와 합치지 않고 **따로 도는 비서 서비스**로 둔다 — 기존 백엔드가 이미 `MOM_ASSISTANT_URL`의 `POST /chat`으로 비서를 부르게 돼 있기 때문이다.

| | 내용 |
|---|---|
| 왜 합치지 않나 | 이름이 겹침(묶음 `backend/app.py` ↔ 기존 `backend/app/`), import 기준이 다름, `psycopg` 3.3.6 ↔ `>=3.2,<3.3` 등 의존성 충돌, 묶음은 CSV·`X-Role` 헤더 시연 서버라 기존 백엔드(PostgreSQL·JWT)와 성격이 다름 |
| 한 일 | 복사본 해시 318행 모두 일치. `config.py`·`demo_state.py`의 경로 2곳만 `생성기/`·`가상사내문서/`로 수정. `.env.example`, 가상환경(Python 3.12.9) 설치, `assistant/변경기록.md` |
| 사내 문서 | `가상사내문서/00_용어집.md` 추가로 8개 파일. 묶음의 문서 읽기 코드로 **195조각** (묶음 MANIFEST와 같음) |
| 시험 결과 | `pytest assistant/backend/tests` 복사 직후: **738 통과 / 478 실패 / 오류 10 / 건너뜀 2**. 원인은 생성기 CSV의 표 이름·열이 묶음이 읽는 것과 달라서다 (예: `alarm_master.csv`는 `alarm_code`, 묶음은 `code` → `KeyError`) |
| 아직 | 조회 도구를 `/api/assistant/tools`(14개) 호출로 바꾸기(5단계), 화면 연결 |

## 2. 비서 서비스 입구(`/chat`) 만들기 — 4단계

기존 백엔드가 `MOM_ASSISTANT_URL`로 부르는 `POST /chat`을 `assistant/backend/chat_service.py`로 만들었다 (`uvicorn backend.chat_service:app --host 127.0.0.1 --port 8100`).

| | 내용 |
|---|---|
| 받는 것·주는 것 | 백엔드 계약 그대로: 질문·화면 문맥·허용 도구·권한 밖 도구·사용자 → `{answer(글자), sources[{doc_name, doc_no, rev, section}], related[], status}`. 상태는 `OK`·`NOT_IN_DOCS`·`OUT_OF_ROLE`·`REFUSED` (실패는 503 `ASSISTANT_UNAVAILABLE` → 백엔드가 `NO_RESPONSE`) |
| 안전 | 서비스 키(`MOM_ASSISTANT_KEY`)가 없거나 틀리면 401. 모델 이름·CLI 경로는 응답에 안 나간다. 외부 Claude는 서버 설정(`ASSISTANT_PROVIDER=claude` + `EXTERNAL_LLM_APP=1`)일 때만 — 요청에 `llm` 칸 없음. 기본은 꺼짐 |
| 채팅 권한 | MTTR·MTBF·센서 값을 묻는 질문은 MNT·MGR 아니면 값 없이 "누가 볼 수 있는지"만 답한다 (묶음에는 없던 규칙이라 서비스가 막음). "MTTR이 뭐야?" 같은 용어 질문은 문서 검색이라 전원 허용 |
| 같이 고침 | `csv_repo.py`: 생성기 기준표(`alarm_master`·`equipment`·`downtime_reason`)의 열 이름에 묶음이 읽는 옛 이름을 더함. 이게 없으면 문서 질문까지 멈췄다 |
| 확인 | 새 시험 33개 통과. 실제 서버를 띄워 **백엔드의 `app/assistant/client.py` 코드로** 호출: 문서 질문 `OK`(출처 용어집 §5), 설비 끄기 `REFUSED`, 엉뚱한 질문 `NOT_IN_DOCS`, 운영자의 MTTR 값 질문 `OUT_OF_ROLE`, 틀린 키 → `ASSISTANT_UNAVAILABLE` |
| 시험 결과 | 이 단계 끝: 1066 통과 / 183 실패 (738 → 1066). 아래 3장에서 마저 풀었다 |

## 3. 운영 데이터를 백엔드 조회 도구로 읽기 — 5단계

비서 서비스(`assistant/`)가 운영 데이터(설비 상태·알람 횟수·지표·생산·로트·작업지시·작업기록·예방 정비·공구 수명·재고·정지)를 **옛 CSV 대신 기존 백엔드의 조회 도구**(`POST /api/assistant/tools/{도구}`)로 읽는다.

| | 내용 |
|---|---|
| 어떻게 | 묻는 사용자 이름(`on_behalf_of`)과 서비스 키를 실어 부른다. 그 역할에 허용되지 않은 도구는 백엔드를 부르기 전에 막고 "볼 수 없어요(값 없음)"로 답한다. 묻는 사용자·허용 도구는 요청마다 따로 둔다(다음 요청에 안 샘) |
| MTTR·MTBF | `reliability` 도구가 허용된 역할(MNT·MGR)에만. 못 보는 역할은 지표 문장에서 MTTR·MTBF가 "—"로도 안 나오고, MTTR 값을 묻는 질문은 백엔드를 부르지도 않고 거절 |
| 지어내지 않기 | 백엔드 도구가 못 주는 정보는 답에서 빼거나 밝힌다: **정지**는 손실 정지만("정지 전체"·필수 정지·순간 정지·계획 정지 말하지 않음), **알람**은 설비·알람별 횟수만(건별·처리 여부·반복 알람 단계 없음), **로트**는 번호로만(작업지시 번호로는 "아직 못 찾는다"). 필요하면 백엔드에 조회 도구를 더해야 한다 — DB/백엔드 담당과 정할 일 |
| 고친 곳 | `tools/query_tools.py`(안쪽 전부), `services/answer.py`(문장 8곳), `repositories/csv_repo.py`(기준표 변환 보강: `control`은 제어기 이름, `doc02_section`은 문서 번호 포함) |
| 시험 | 새 시험 89개 통과. 기본 가짜 백엔드를 옛 시험에 끼워 **1239 통과 / 실패 0 / 예상 실패 76 / 건너뜀 2**. 예상 실패 76개는 이름과 까닭을 `assistant/backend/tests/legacy_expected_failures.py`에 적었다: 옛 모의 API 47, 묶음 밖 파일 7, 정지 문장 변경 6, 옛 CSV 값 기대 9, 문서 개정 차이 7 |
| 문서 답 불변 확인 | 평가 질문 1,018개를 조회 도구 교체 전과 지금 같은 문서로 비교: 전에도 답했던 687개는 모든 칸이 똑같고, 전에 오류였던 운영 질문 331개는 이제 모두 답한다 |
| 실제 HTTP 확인 | 임시 백엔드 서버 + 비서 서비스를 띄워 **기존 백엔드의 `app/assistant/client.py`로** 호출: 보전 담당자 OEE 질문은 `kpi`+`reliability`, 작업자는 `kpi`만, 작업자의 MTTR 질문은 임시 백엔드까지 안 감, 허용 안 된 도구는 안 부름, 백엔드 꺼짐 → `ASSISTANT_UNAVAILABLE` |
| 아직 | 진짜 백엔드·DB와 붙여 보기, 외부 Claude 켜 보기(기본 꺼짐), 이어 묻기, 화면(이브 채팅 탭) 연결, 날짜 기본값을 실시간 시계에 맞추기 |

## 4. 공용 DB에 붙여 켜 보기 준비와 실행 안내 문서

| | 내용 |
|---|---|
| 한 일 | 백엔드 `.venv`를 팀 `requirements.txt`로 설치, 공용 Supabase(`mom-db`)에 붙는 설정 파일을 내 PC에만 만듦(git 무시). **접속 점검 4개 모두 OK**(앱 계정·읽기 전용 계정·실시간 알림·왕복 17ms). 백엔드(8020)와 비서 서비스(8100)를 켜서 `health`·키 거절(401)·끄기까지 확인 |
| 안전 | 공용 DB 쪽 쓰기 기능을 못 쓰게 `MOM_DEMO_MODE=false`·`MOM_RUN_WORKERS=false`. 비밀번호는 파일에만(채팅에 안 올림). Supabase 관리 토큰은 쓰지 않음 |
| 포트 | 새 백엔드는 **8020**. 8000·8010은 내 원본 프로젝트의 옛 모의 서버가 쓰고 있어서(끄지 않음) 피했다 |
| 고친 것 | `assistant/.env.example`의 값 옆 `# 설명`을 윗줄로 — 코드가 설명까지 값으로 읽어 `EXTERNAL_LLM_APP=1   # …`가 조용히 안 켜지는 함정이 있었다. 시험 4개 추가 |
| 새 문서 | `assistant/실행_안내.md` (지금 상태에서 켜는 법). 끝에서 끝 확인 스크립트 `assistant/e2e_check.py` |
| **끝에서 끝 확인** | 시연 비밀번호로 U01(작업자)·U07(보전 담당자)에 로그인해 **진짜 백엔드 + 공용 DB**에서 비서 질문 8개: **8/8 맞음**. 문서 질문 `OK`(출처 용어집 §5), 설비 끄기 `REFUSED`, 작업자의 MTTR `OUT_OF_ROLE`(값 없음), 작업자의 재고 `OK`, 보전 담당자의 OEE·MTTR(MTTR 113.5분)·공구 수명·알람 2075 횟수 `OK`(출처 DOC-02 §4.11·DOC-03 §2.11) |
| 공용 DB에 남은 기록 | `chat_log` 8줄(chat_id 1~8: U01 1~4, U07 5~8), `access_log` 약 20줄(로그인 2·비서 질문 8·조회 호출 약 9), U01·U07 마지막 로그인 시각 — **DB 담당이 지워 주기로 한다** |
| 아직 | 외부 Claude를 켠 채 진짜 DB로 묻기, 화면 연결, 작업자의 OEE 질문에서 MTTR이 빠지는지를 진짜 DB로 확인(가짜 백엔드 시험으로만 확인함) |

## 5. 채팅 탭은 외부 LLM(Claude)으로 — 확정과 첫 시험

| | 내용 |
|---|---|
| 결정 | 이브 채팅 탭은 **외부 LLM(Claude)** 으로 하기로 확정 (2026-10-16, AI 비서 담당). 기획서의 "로컬 LLM 확정"과 달라진 점이라 **팀 문서와 맞추는 일이 남음**. 실제 자료는 반출 승인 전까지 쓰지 않는다(지금 데이터는 모두 가상) |
| 켠 곳 | 내 PC의 `assistant/.env`(git 무시). `.env.example`은 안전하게 꺼진 채 둠 |
| 첫 시험 | 가짜 백엔드·가상 데이터, 질문 4개: 문서 질문 20.5초(외부 호출 5회), 재고 7.3초(2회), 알람 카드 2개는 0초(0회, 규칙만 — 안전 관련 답은 외부로 안 나감). 단계 실패 없음 |
| 시간 제한 | 백엔드가 비서를 기다리는 기본 30초 → 내 PC `.env.supabase`에 `MOM_ASSISTANT_TIMEOUT_SECONDS=130`. 화면(Next.js) 프록시도 기본 30초 — `next.config.mjs`의 `proxyTimeout`은 **팀 파일이라 아직 안 고침** |
| **진짜 DB + 외부 Claude 확인** | 같은 날 Claude를 켠 채 U01·U07로 8개 질문: **8/8 맞음, 전체 62초** (문서 질문 20.9초, 운영 조회 7.6~8.5초, 거절·권한 밖 0.1~0.2초). 숫자(OEE 68.0%, MTTR 등)가 규칙 답과 똑같이 유지됨. `claude` 프로세스 안 남음. 공용 DB 기록은 2회분: `chat_log` chat_id 1~16 (U01: 1~4·9~12, U07: 5~8·13~16) |
| 아직 | 여러 명이 동시에 물을 때의 시간·구독 한도, 서비스를 켤 PC(`claude` 로그인된 PC)와 사용자별 한도 정하기, 화면 연결 |

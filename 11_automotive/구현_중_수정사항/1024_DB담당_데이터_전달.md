# 1024 DB 담당 전달 — 최종용 데이터와 문서·데이터 연결 점검

> 2026-10-24 밤. **이제 데이터는 더 안 고친다**(확정). 이 문서는 DB 담당이 공용 DB에 올릴 때 필요한 것과, 문서↔데이터 연결을 어떻게 확인했는지를 모았다. 코드·데이터는 PR #146(`feat/profile-generator-20261024`)에 있다.

## 1. 한 줄 결론

최종용 데이터(`생성기/out_final/` + `생성기/out_realtime_final/`)를 **실제 PostgreSQL 16에 우리 스키마(`db/apply.sh`)를 적용한 뒤 `tools/load_generated.py`로 넣어 봤고, 55개 표가 오류 없이 들어갔다. `db/checks/validate_loaded_data.sql` 20개 규칙 모두 OK**(확인 필요 0건). 영상용도 똑같이 확인했다.

## 2. 넣는 방법 (그대로 해 보면 된다)

```bash
# 1) 생성기 폴더에서 센서 CSV 만들기 (깃에 없음, 약 15초)
cd 생성기 && .venv\Scripts\python generate.py --profile final        # → out_final/ (센서 CSV 포함)
.venv\Scripts\python realtime.py --profile final                     # → out_realtime_final/ (이미 깃에 있음, 다시 만들어도 같음)

# 2) 빈 DB에 스키마 → 적재 (backend 폴더, PGHOST 등은 그대로)
./db/apply.sh
python tools/load_generated.py ../생성기 --psql "psql -d mom" --out-dir out_final --rt-dir out_realtime_final --realtime
psql -X -q -v ON_ERROR_STOP=1 -f db/checks/validate_loaded_data.sql   # 20줄 모두 OK 여야 함
```

- `tools/load_generated.py`에 **`--out-dir`·`--rt-dir` 두 옵션을 추가**했다 (기본값은 옛 이름 `out`·`out_realtime`이라 지금까지 쓰던 방식은 그대로 된다). 이 한 가지만 DB 담당 파일을 건드렸다.
- 센서(`--sensor`)는 이번 점검에서 빼고 확인했다. 크기: `out_final/sensor_sample.csv` 826,414줄(44MB) + `out_realtime_final/sensor_sample.csv` 9,661줄. Supabase 무료 500MB를 보고 넣을지 정해 주세요.
- 실시간 쪽은 **덮어쓰기(upsert)** 로 들어간다: `production_order`, `production_lot`, `inspection_plan`, `lot_hold`(기본 키가 같으면 실시간 것으로 바뀜). 나머지는 이어 붙임.

## 4. 문서↔데이터 연결 점검 (`생성기/check_links.py`)

과거 + 실시간을 **DB에 넣는 모양대로 합쳐서** 본다. 두 프로필 모두 **통과 20 / 실패 0**.

| 점검 | 결과 |
|---|---|
| 번호 중복 없음 (기본 키 21개 표, 복합 키: 작업 단계·체크·부품) | ✅ |
| 외래 키 — 가리키는 값이 있음 (60여 개 관계, 합친 데이터) | ✅ |
| OP-30 정지 알람마다 작업지시서 1건 (충돌 연쇄는 마지막 992에만) | ✅ 8건 = 8건 |
| 작업기록서(정식) = 작업지시서 1건씩, 같은 알람·설비·로트 | ✅ |
| 작업지시서 시각: 알람 직후 생성(≤5분) → 승인 → 완료 | ✅ |
| 작업기록서 시각: 시작 = 알람, 끝 = 알람 풀림, 확정 ≥ 끝, 수리 시간 = 끝 − 시작 | ✅ |
| 작업기록 체크 = 잠금·표지 9단계 + 작업 단계 수, 순번 연속 | ✅ |
| 사용 부품 ↔ 재고 거래(사용) 수량 일치 | ✅ |
| 정지(DOWN)가 있는 OP-30 알람 ↔ 작업지시서 | ✅ |
| 비서 의심 로트 보류: 충돌(992)이면 그 알람의 작업지시서 있음 | ✅ |
| 문서 버전: 문서마다 v0~현재 버전이 `document_revision`에 있음 (DB 점검 R-35와 같은 규칙) | ✅ |
| 실시간 번호가 과거 마지막 번호 바로 다음, 상태 구간 이음, 근무일·교대가 같이 들어 있음 | ✅ |

**점검 중 찾아서 고친 것 (모두 반영됨)**: ① 실시간 구간에 문서 버전(v0)이 없어 DB 점검 R-35에 2건 → 작업지시서·작업기록서·예방 정비 기록의 문서 버전을 만들도록 ② 실시간 기록이 가리키는 `shift`·`work_day`(10/26·10/27)가 안 들어 있어서 → `out_realtime_final/`에 같이 내보냄 ③ 작업기록서의 사용 부품이 재고 거래로 안 이어짐 → 재고 거래(`WORK_RECORD`)로 이어짐.

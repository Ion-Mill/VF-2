## 1. 지금 상태 (왜 필요한가)

- 화면 기본값이 **백엔드 모드**(화면 → 백엔드 → DB)라서, 관리자가 직원 관리를 열면 **"백엔드 연결에 아직 없는 화면 기능이에요"** 오류가 난다 (`frontend/src/shell/backendApi.ts`에 `staff` 길이 없음).
- 예전에는 시연 서버(`frontend/tools/sim_server.py`)가 이 API를 대신했다. 그 코드가 그대로 본보기다.
- 요구사항 `FR-USR-01-11`은 지금 **"역할 바꾸기·계정 만들기·켜고 끄기는 넣지 않는다"** 이다. B를 하려면 이 줄을 바꿔야 한다 (5-3).

## 2. 묶음 A — 조회·배치 (명세 있음, 그대로 만들기)

### 2-1. 만들 주소

| 번호 | 주소 | 하는 일 |
|---|---|---|
| API-USR-01 | `GET /api/staff?period=` | 직원 명단 + 배치표 + 담당 0명 칸 + 사람마다 역할별 숫자 4칸 |
| API-USR-02 | `GET /api/staff/{user_id}/activity?period=&size=` | 한 사람의 숫자 4칸 + 최근 한 일 목록 (최신이 위) |
| API-USR-03 | `PATCH /api/staff/assignments` | 담당 교대·담당 공정 바꾸기 (여러 명 한 번에) |

- **본보기**: `frontend/tools/sim_server.py`의 `staff_api()`, `frontend/tools/server_staff.py`(`KPIS`·`past_events`·`live_events`·`period_range`·`kpis`·`board`·`check_change`). 계산 방법은 다 있고, **CSV 읽는 부분만 DB 조회로** 바꾸면 된다.
- 명세 원문: `API명세서_v1.md` 205~209줄, 요구사항 `FR-USR-01-01~12`, UI `SCR-27`.

### 2-2. 규칙 (명세 그대로)

| 규칙 | 내용 |
|---|---|
| 권한 | **관리자(MGR)만** 읽기·바꾸기 (NFR-SEC-04·05). 시연 서버는 `?role=MGR`로 봤지만, 백엔드는 **로그인 토큰의 역할**로 확인 |
| 새 표 없음 | 기존 표의 "누가" 칸을 사람별로 모은다 (FR-USR-01-10) — 아래 2-3 |
| 넣지 않는 것 | 이브 채팅 기록, 순위·점수 (FR-USR-01-11) |
| 숫자 4칸 | 역할마다 다름 (`server_staff.py` `KPIS`). 평균 없이 합계만, 양품률만 비율 |
| 배치 바꾸기 | `app_user`의 `home_shift_type`·`home_process_code`·`home_process_code_2`. 같은 역할만 그 줄에(공정 = OPR, 보전 = MNT, 반장 = SUP), 담당 공정 최대 2개. 어기면 `VALIDATION` |

### 2-5. 정해 주세요 — 기간 값 `sep`

명세의 기간 값 `today`·`7d`·`30d`·`sep` 중 **`sep`(9월 전체)은 9/1~10/1 고정**이라 10월 데이터에서는 빈 결과다. **`all`(기록 시작 ~ 지금)로 바꾸기를 제안**한다 [제안]. 정해지면 화면 버튼 이름을 "기록 전체"로 바꾼다.

## 3. 묶음 B — 직원 추가·수정 (새로 제안) [제안]

### 3-1. 하고 싶은 것

| 기능 | 설명 |
|---|---|
| 직원 추가 | 이름·역할·담당 교대·담당 공정·처음 비밀번호를 넣어 새 직원을 만든다 |
| 직원 정보 고치기 | 이름, 역할을 고친다 (담당 교대·공정은 A의 배치 바꾸기로) |
| 사용 중지 · 다시 사용 | 그만둔 직원은 **지우지 않고 사용 중지**한다 (`is_active = false`). 로그인할 수 없고 배치표에서 빠진다. 지난 업무 기록의 이름은 그대로 남는다 |
| 비밀번호 다시 정하기 | 관리자가 새 비밀번호를 정해 준다 |

**지우기는 만들지 않는다**: 요구사항 데이터 보존 규칙(사용자 계정은 지우지 않고 비활성)과 지난 기록의 "누가" 칸 때문이다.

### 3-2. 주소 (초안)

| 번호(가칭) | 주소 | 받는 값 | 돌려주는 값 |
|---|---|---|---|
| API-USR-04 | `POST /api/staff` | `user_id`(비우면 다음 번호, 예: `U13`), `user_name`, `role_code`, `home_shift_type`, `home_process_code`, `home_process_code_2`, `password`, `reason`(선택) | 만든 직원(비밀번호 빼고), `revision_id` |
| API-USR-05 | `PATCH /api/staff/{user_id}` | 바꿀 칸만: `user_name`, `role_code`, `is_active`, `password`, `reason`(선택) | 바뀐 직원(비밀번호 빼고), `revision_id` |

### 3-3. 규칙 (초안)

| 규칙 | 내용 |
|---|---|
| 권한 | 관리자(MGR)만. 토큰의 역할로 확인 |
| 아이디 | DB 제약 그대로 `^[A-Za-z0-9_]{2,20}$`. 이미 있으면 `409 DUPLICATE`. 비우면 `U` + 다음 두 자리 |
| 이름 | 1~40자 (`varchar(40)`) |
| 역할 | `OPR`·`MNT`·`SUP`·`MGR` 중 하나 |
| 담당 공정 | 두 번째 담당 공정은 **OPR만**, 첫째와 달라야 함 (DB 제약 `ck_app_user_process_2`). 역할을 OPR에서 다른 역할로 바꾸면 `home_process_code_2`를 비운다 |
| 비밀번호 | 서버에서 scrypt로 바꿔 `password_hash`에만 저장 (`app/domain/passwords.py`의 `hash_password`). **원문은 저장·로그·응답·수정 이력 어디에도 남기지 않는다**. 최소 길이는 [선택 필요] |
| 자기 자신 | 지금 로그인한 관리자는 자기 자신을 사용 중지하거나 MGR이 아닌 역할로 바꿀 수 없다 |
| 관리자 최소 1명 | 사용 중인 MGR이 0명이 되는 변경은 거절 (`VALIDATION`) |
| 사용 중지 | 로그인 거절은 이미 됨(`auth.py`가 `is_active` 확인). **이미 받은 토큰도 막아야 한다** — 토큰 확인 때 `is_active`도 보는지 확인 부탁 |
| 바꾼 기록 | A와 같이 `document_revision`(`APP_USER`)에 남긴다. 추가 = v0 "직원 추가", 수정 = 바뀐 칸 전·후. 비밀번호는 값 없이 **"비밀번호 바꿈"** 한 줄만 |
| 공용 DB | 공용 Supabase에서도 쓰기가 일어난다. 발표 때 평가자가 직원을 만들지 않게, 관리자 계정은 발표자만 쓰는 것으로 정한다 [선택 필요] |

## 9. 백엔드 답 (2026-10-25 백엔드 담당 — A·B 모두 만듦, `1025_수정간단내용.md` 61장)

사용자(백엔드 담당) 결정: **"A·B 다 한다."** 백엔드에 다섯 주소를 모두 만들고, 백엔드 확인에서 나온 다섯 가지를 고쳤다.

### 9-1. 만든 주소 (모두 관리자만 — 권한 `STAFF`)

| 번호 | 주소 | 이 문서와 다른 점 |
|---|---|---|
| USR-01 | `GET /api/staff?period=&include_inactive=` | 기간에 **`all`(기록 전체 = 첫 교대부터)** 을 더함, `sep`도 그대로 받음 (2-5). 명단은 **사용 중인 직원만**이 기본, `include_inactive=true`면 사용 중지도 맨 뒤. `shift`·`users[].on_shift`·`kpis`(`label`·`value`·`unit`)·`board`·`empty`는 시연 서버와 같은 모양 |
| USR-02 | `GET /api/staff/{user_id}/activity?period=&page=&size=` | `size` 처음 값 80 (최대 500), `page` 더함. `items` = `at`·`kind`·`text`·`screen`·`key` (시연 서버와 같음) |
| USR-03 | `PATCH /api/staff/assignments` | 화면이 보내는 **`procs`(담당 공정 목록)도 받음** (명세 칸 `home_process_code`·`home_process_code_2`도 받음, 비우려면 `""`). 한 사람이라도 틀리면 아무것도 안 바뀜. 돌려주는 값 `{changed: [{user_id, revision_id, version_no}], users, board, empty}` |
| USR-04 | `POST /api/staff` | 3-2 그대로. 돌려주는 값 `{user, revision_id, version_no}` (비밀번호·해시 없음) |
| USR-05 | `PATCH /api/staff/{user_id}` | 3-2 칸 + 역할을 바꾸며 같이 정할 수 있게 `home_shift_type`·`procs`도 받음 (보통은 USR-03) |
| (더함) | `GET /api/users` | **로그인한 누구나** — `{users: [{user_id, user_name, role_code, home_shift_type, home_process_code, home_process_code_2, is_active}]}` (시연 서버 `users`와 같은 모양). 화면 `App.tsx`가 모든 역할에서 부르는 `users`(배치 바로 적용, FR-USR-01-06)가 백엔드 모드에서 빈 목록이던 것, 새 직원 이름 표시(4장)에 쓴다 |

오류는 API명세서 1장 코드만 쓴다: 규칙 위반 = **422 `VALIDATION`** (시연 서버는 400이었음) + `detail.reason` (`SELF`·`LAST_MGR`·`PROCESS_ROLE`·`PROCESS`·`SHIFT`·`NAME`·`ROLE`·`USER_ID`·`PASSWORD`·`INACTIVE`·`NO_CHANGE`), 같은 아이디 = **409 `INVALID_STATE`** + `reason: DUPLICATE`, 없는 직원 = 404, MGR 아님 = 403.

### 9-2. 백엔드 확인 1~5 고친 것

| # | 문제 | 고친 것 |
|---|---|---|
| 1 | 설정 `PATCH /api/settings/users`(SET-03)가 확인·수정 이력 없이 `app_user`를 바로 고침 (두 번째 공정 비우기 불가, 자기 자신·관리자 0명 확인 없음, 역할 바꾸면 DB 제약 오류) | SET-03 고치기도 **직원 관리와 같은 길**(`backend/app/services/staff.py update_user`) — 같은 확인, 수정 이력, 같은 돌려주는 값 |
| 2 | 수정 이력 표가 `APP_USER`를 받지 못하고, 받아도 아무도 못 봄 | DB: 문서 종류 CHECK에 `APP_USER`, `fn_doc_status`가 `ACTIVE`/`INACTIVE`. 서버: 보기 권한 `APP_USER → STAFF` (MGR만). 공용 DB용 `backend/supabase/migrations/20261025010000_staff_1025.sql` (**아직 공용 mom-db에 안 올림**) |
| 3 | 직원 관리용 권한 대상이 없음 | 새 대상 `STAFF` (`EDIT` = MGR, 보기 = MGR) |
| 4 | 3-3 "이미 받은 토큰도 막아야" | 바꾸는 주소는 원래 요청마다 `is_active`를 봄. 1초마다 부르는 3D 라인 뷰도 이제 **60초 기억한 사용자 상태**로 사용 중지·역할 변경을 막음 (401 → 다시 로그인) |
| 5 | 비밀번호 바꾸는 API가 없었음 (8장 표기가 틀렸음) | USR-05 `password`. 최소 길이 `MOM_PASSWORD_MIN_LENGTH` 기본 **8** [선택 필요 — 6장 4번] |

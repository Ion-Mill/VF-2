# [정비] 기능 구현 계획

> 담당: 장우석 / 대상: MNT-01~05 + ML-01 + 정비 관련 알림(AST-02)
> 근거: 기획서(`AUTOMOTIVE_MACHINING_MOM_PLATFORM_PLAN.md`), 가상 데이터 설계서(`AUTOMOTIVE_MACHINING_SYNTHETIC_DATA_PLAN.md`), `docs/haas/`, `docs/kosha/`, `gemini/teammate_gemini_share_text.txt`, 그리고 새로 만든 [알람 원인·조치 카탈로그](../maint_docs/maint_cause_action_catalog.csv)
> 표시: **[제안]** = 이 문서에서 새로 제안한 것, 팀 확정 필요 / **[실제]** = 문서 원문에 있는 것 / **[가상]** = 팀이 정하는 값
> 상태: 초안. 안 A/B와 설비 범위는 팀 미결정이라 **기본 가정**을 두고 설계했다 (9장).

---

## 1. 한 줄 요약

**알람 번호 → 원인·조치 표(카탈로그) → 지침 카드 → 작업지시서 → 정비 이력** 한 줄을 끝까지 되게 만든다.
규칙과 표로 되는 것은 코드가 처리하고, AI(LLM)는 **요약, 서식 채우기, 메모 정리, 질문 답변**에만 쓴다. 안전 절차는 AI가 쓰지 않고 **고정 서식**으로 붙인다.

## 5. 기능별 구현

### 5.1 MNT-02 알람 대응 지침 카드 (필수)

**하는 일:** 알람이 발생하면 카드를 자동으로 만들어 화면에 띄운다.

**처리 순서**

| 단계 | 처리 | 방식 |
|---|---|---|
| 1 | 알람 번호로 알람 목록에서 **정확히 일치하는 NGC 항목** 가져오기 | 규칙(SQL) |
| 2 | `alarm_guide_map`에서 심각도, 정비 필요 여부, 연결된 카탈로그 행 가져오기 | 규칙 |
| 3 | 카탈로그 행을 증거 수준 순으로 정렬: **직접 → 공용 절 → 알람목록** | 규칙 |
| 4 | 정렬된 상위 행만 LLM에 넣어 "먼저 할 일" 3~5줄로 요약 | **LLM** (입력은 카탈로그 행으로 한정) |
| 5 | 정비가 필요한 알람이면 안전 고정 서식 붙이기 (A6 매트릭스 기준) | 고정 서식 |
| 6 | 같은 알람의 이번 주 횟수와 지난 원인 한 줄 | 규칙(SQL) |

**카드 칸:** 알람 번호·영문·한국어 이름 / 심각도 [가상] / 알람 목록 설명 / 먼저 할 일 / 누가(작업자·보전) / 안전 / 지난 기록 / 출처 / 버튼

**데이터로 확인한 구현 포인트**

- 카탈로그의 `action_ko`는 대부분 `→`로 단계가 나뉘어 있다. **작업지시서의 작업 순서는 LLM 없이 이 구분자로 나눠서 만들 수 있다.**
- 카탈로그에 `evidence_level`이 있어서, 카드에 "직접 근거(TSG 증상표)"와 "관련 점검(공용 절)"을 구분해 보여줄 수 있다. 예: 992의 절삭유 오염 점검은 **공용 절**이므로 "관련 점검"으로 표시.
- 근거가 알람 목록 설명뿐인 알람(362, 314)은 카드에 "문서의 안내 수준: 알람 설명"이라고 표시하고, **LLM에게 추가 원인을 만들지 못하게** 한다.
- 카탈로그 `note`의 발생 조건(예: 2073·2075는 윤활 주기 5회 연속 실패 때 발생)은 카드의 "참고"로 보여줄 수 있다.
- `applies_vf2_ngc`가 "조건부"인 행(60A 앰프)은 카드에 조건을 같이 표시한다.

**LLM 가드레일** [제안]

1. 입력으로 준 카탈로그 행 밖의 원인·조치·숫자를 쓰지 않는다.
2. 숫자(전압, 시간, 길이)는 요약에서 **프로그램이 원문 값과 대조**한다. 맞지 않으면 요약을 버리고 카탈로그 원문을 그대로 보여준다.
3. 안전 문구는 LLM이 쓰지 않는다. 고정 서식에서 가져온다.
4. LLM이 실패하거나 시간이 오래 걸리면 카탈로그 원문 행을 그대로 보여준다 (카드는 반드시 뜬다).

**카드 예시 (S1, 알람 992)**

```
[정지] VF2-01 · 992 AMPLIFIER OVER CURRENT (전류가 높은 증폭기)
먼저 할 일
  1. 선행 축 알람으로 해당 축 확인 (108 → 994 → 992 순서면 충돌 의심)
  2. 이송 경로 간섭, 외함·주축·공구 손상 확인
  3. 충돌 징후가 없으면 볼스크류·리니어 가이드가 손으로 자유롭게 움직이는지 확인
관련 점검: 모터 파워 케이블 커넥터의 절삭유 오염 (증거 수준: 공용 절)
안전: 메인 차단기 OFF, 제어 캐비닛 작업 전 고전압 표시등 꺼진 뒤 5분  [Haas TSG 전기 안전]
      잠금·표지 필요 [KOSHA B-M-25-2026]
지난 기록: 이번 달 2번째 · 지난 원인: ... (MW-0914)
출처: Servo Amplifier – Troubleshooting Guide – NGC › Alarm 992
[더 묻기] [작업지시서]
```

**완료 기준:** S1 알람 순서(108→994→992)를 넣으면 3초 안에 카드가 뜨고, 카드의 모든 문장에 출처가 있다. 15개 알람 모두 카드가 만들어진다(314는 "작업지시서 불필요" 표시).

### 5.2 MNT-03 정비 작업지시서 (필수)

**하는 일:** 지침 카드를 작업지시서 서식으로 바꿔 초안을 만든다. 보전 담당자가 고치고 승인한다.

**채우는 방법**

| 칸 | 방법 | 비고 |
|---|---|---|
| 번호, 설비, 알람, 작성자, 시각 | 자동 | 번호 형식 `MW-0001` [제안] |
| 제목, 증상 | 카드에서 규칙으로 | 알람 이름 + 설비 |
| **작업 순서** | 카탈로그 `action_ko`를 `→`로 분할 | LLM 불필요. 담당자가 편집 |
| **작업 전 안전 6단계 + 해제 3단계** | 고정 서식 | KOSHA B-M-25-2026 6.1~6.6, 7.1~7.3 |
| 고전압 대기 | 고정 문구 (해당 알람만) | A6 매트릭스 |
| 보호구 | 고정 문구 | 법 제95조, KOSHA 자료 |
| 차단 지점 | 설비 마스터에서 | [가상] 2~3개씩, **먼저 정해야 함** |
| 비슷한 과거 작업 | 같은 알람·설비 이력 링크 | MNT-05 |
| 필요 공구·부품, 예상 시간 | 담당자 입력 | 부품 이름은 카탈로그 원인에서 후보 제안 |

**상태 흐름과 권한** (기획서 11장, Gemini 상태값 재사용)

```
DRAFT(초안) ──승인(MNT/MGR)──▶ APPROVED ──착수(MNT)──▶ IN_PROGRESS ──완료(MNT)──▶ COMPLETED
    └────────────취소(MGR)────────────────────────────────────────────▶ CANCELLED
```

| 전이 | 조건 (서버에서 검사) [제안] |
|---|---|
| DRAFT → APPROVED | 승인자 역할이 MNT 또는 MGR, 차단 지점이 1개 이상 입력됨 |
| APPROVED → IN_PROGRESS | **작업 전 안전 6단계가 모두 체크됨** (체크 없으면 착수 불가) |
| IN_PROGRESS → COMPLETED | 해제 3단계 모두 체크, 원인(카탈로그 `cause_id` 또는 직접 입력), 조치, 수리 시간 입력 |
| 어느 상태 → CANCELLED | 역할이 MGR |

- 설비를 원격으로 조작하는 기능은 없다 (기획서 원칙 5). 잠금·표지 체크는 **현장에서 한 일을 사람이 기록**하는 것이다.
- 안 B를 고르면 정지 등급 알람에서 초안이 **자동으로 생성**되고 담당자가 지정된다. 구조는 같고 "생성 트리거"만 다르게 둔다 (9장).

**완료 기준:** 카드에서 [작업지시서]를 누르면 안전 6+3단계가 빠짐없이 들어간 초안이 생기고, 6단계를 체크하지 않으면 착수가 거부된다.

### 5.3 MNT-05 정비 이력 기록·검색 (권장)

**하는 일:** 작업지시서가 완료되면 이력으로 저장하고, 같은 알람·같은 설비의 과거 조치를 찾아 준다.

| 부분 | 방식 |
|---|---|
| 완료 시 이력 저장 | 작업지시서 → `maintenance_history` 복사, 수리 시간 계산 |
| 반복 횟수 ("이번 주 3번째") | SQL (알람 + 설비 + 기간 count) |
| 검색 1단계 | 알람 번호·설비·기간으로 조회 (규칙) |
| 검색 2단계 (여유 있으면) | 비슷한 문장 찾기 |
| **메모 정리 (AI)** | 작업자의 대충 쓴 메모 → `원인 / 조치 / 교체 부품` 칸 |

**메모 정리 설계** [제안]

- 입력: 메모 + 해당 알람의 카탈로그 원인 후보 목록(`cause_id`와 `cause_ko`)
- 출력(JSON): `cause_id`(후보 중 하나 또는 `OTHER`), 조치 요약, 교체 부품, 신뢰도
- 후보에 없으면 `OTHER`로 두고 사람이 확인한다 (억지로 후보에 끼워 맞추지 않음)
- 예: "앰프 쪽 냄새남, 케이블 봤는데 절삭유 묻어있음" → `C-993-04` 또는 `C-993-05` 후보 제시, 사람이 선택

**완료 기준:** 가상 메모 샘플 20개를 넣었을 때 정리 결과의 `cause_id`가 정답과 일치하는 비율을 측정한다. (목표값은 팀이 정함)

### 5.4 MNT-04 예방 정비 일정 (권장)

**하는 일:** 정비 일정을 설비별 달력으로 보여주고, 기한이 된 항목을 알린다. 실시하면 기록한다. **AI를 쓰지 않는다.**

**데이터 처리**

1. `howto_vmc_maintenance_schedule.txt`에서 `부위 / 항목 / 주기` 추출 (A7). 원문 주기 값: `Daily`, `Weekly`, `Monthly`, `Six Months`, `Annually`, `Two Years`, `Four Years`, `As Required`
2. VF-2 기본 사양만 선별 (50T 기어박스, 로터리, 팔레트 관련 등 **옵션 항목은 제외**). 선별 결과는 `pm_task.applies_vf2`로 남긴다.
3. 주기 → 일수 변환표: Daily=1, Weekly=7, Monthly=30, Six Months=182, Annually=365 ... **As Required는 기한 계산 안 함** [제안]

| 테이블 | 핵심 칸 |
|---|---|
| `pm_task` | `task_id`, 부위, 항목(영·한), `interval_code`, `interval_days`, `applies_vf2`, `safety_required` |
| `pm_record` | `record_id`, `task_id`, `equipment_id`, `due_date`, `done_at`, `done_by`, `status`(제때/늦음/미실시) |

- 기한 판정은 `done_at` 마지막 값 + `interval_days`로 계산한다. **기한 임박 / 초과** 상태는 쿼리로 구한다.
- S2 시나리오: "축 윤활유 탱크 점검(매월)"이 기한을 넘기면 알림이 뜨고, 이후 2075 알람이 나오면 카드가 "이 설비의 월간 점검이 N일 지났습니다"를 보여준다. 이 연결은 카탈로그 C-2075-03(`월간 점검 소홀`)의 근거 문장과 맞는다.

**완료 기준:** 설비별 달력에서 항목이 보이고, 시연용 연체 항목 2~3개가 초과로 표시되며, 실시 기록을 입력하면 기한이 다음 주기로 갱신된다.

### 5.5 MNT-01 질문 답변 (필수, 위험이 가장 큼)

**하는 일:** 한국어로 물으면 문서와 운영 기록에서 찾아 답하고 출처를 붙인다.

**질문 종류별 처리**

| 종류 | 예시 | 처리 |
|---|---|---|
| 알람 번호가 들어간 문서 질문 | "992 뜨면 뭐부터 봐?" | **① 알람 목록 정확 조회 → ② 카탈로그 → ③ TSG 해당 절 검색** 순서. 카탈로그에 있으면 카드와 같은 근거로 답 |
| 알람 번호 없는 문서 질문 | "제어반 열기 전 얼마나 기다려?" | 문서 검색 (TSG, KOSHA, 매뉴얼) |
| 운영 질문 | "어제 야간에 VF2-01 몇 번 멈췄어?" | **조회 도구** 호출 (SQL을 AI가 쓰지 않음) |
| 섞인 질문 | "2075가 왜 자꾸 떠?" | 이력 조회 + PM 기한 조회 + 카탈로그 |

**검색 구성** [제안]

- **1순위 소스는 카탈로그**: 원인·조치가 구조화돼 있어 정확도가 높다. 한국어 요약이 있어서 한국어 질문과 매칭하기 쉽다.
- **2순위 소스는 TSG 원문**: 절 단위로 조각을 만들고, 각 조각에 `문서명`, `절 제목`, `제어기 세대`, `가상 여부`를 붙인다. 제어기 세대는 `tsg_collection_summary.csv`의 `control_generation`을 쓴다. **알람 질문에는 NGC·both만 검색**한다.
- 3순위: 조작 매뉴얼(한국어), KOSHA, 가상 사내 문서 ("가상 사내 문서"라고 출처에 표시)
- 출처 형식: `문서명 › 절 제목` (웹 문서는 쪽 번호가 없음)

**조회 도구 (정비 몫)** [제안] — 입력/출력은 A9에서 확정

| 도구 | 하는 일 |
|---|---|
| `get_alarm_info(alarm)` | 알람 목록 + 카탈로그 |
| `get_alarm_history(equipment, from, to, alarm?)` | 알람 발생 이력, 반복 횟수 |
| `get_work_orders(equipment?, status?)` | 작업지시서 목록 |
| `get_maint_history(alarm?, equipment?)` | 정비 이력 |
| `get_pm_due(equipment?, within_days?)` | 예방 정비 기한 |
| `get_tool_life(equipment?, threshold?)` | 공구 수명 현황 |
| `search_docs(query, controller_gen)` | 문서 검색 |

**가드레일** (기획서 14장 위험 2·3과 동일)

1. 찾은 조각만으로 답한다. 못 찾으면 "문서에 없음"이라고 답한다.
2. 출처 없는 답은 표시하지 않는다.
3. 안전 절차 질문은 고정 서식으로 답한다 (AI가 새로 쓰지 않음).

**1주차에 먼저 시험할 것:** 한국어 질문으로 영어 TSG를 잘 찾는지. 시험 방법은 카탈로그에서 질문-정답 20~25개를 만들어(A12) **카탈로그 한국어 요약 검색 vs 영어 원문 검색**의 적중률을 비교한다.

**완료 기준:** 평가 질문 세트(정비 몫 20~25개)에서 정답 문서·절 일치율을 숫자로 낸다.

### 5.6 ML-01 공구 수명 관리 (권장, 일정이 밀리면 줄임)

| 부분 | 방식 | 데이터 |
|---|---|---|
| 사용 횟수·남은 수명 화면 | **규칙**: 부품 1개 가공 = 사용 1회, 한도 대비 % | 가상 (`tool`, `tool_usage`) |
| 90% 알림, 100% 알림 | 규칙 (알림 규칙표) | 알람 362·174 연결 |
| 예측 모델 | LightGBM, 실제 Haas VF-1 실험 데이터로 학습 | `../8_Haas_VF-1_milling/` |

- 기본 화면은 **사용 횟수 기준**이다. 모델은 "실제 데이터로 한 예측 실험"으로 별도 표시한다 (처음 보는 공구 R² 0.55~0.65 수준이라 단정하지 않는다).
- 공구 마스터와 한도는 A11에서 정한다 (VF-2 한 대당 8~12개, 한도는 [가상]).
- 알람 362의 조치(만료 공구 검사 → 오프셋 업데이트 → ATM 탭에서 사용 계수기 초기화)는 카탈로그 C-362-01에 있다.

### 5.7 정비 관련 알림 규칙 (AST-02의 정비 몫)

알릴지 말지는 **규칙**이 정하고, AI는 알림 문장만 붙인다. [제안] 값은 모두 [가상].

| 공구 수명 한도 | 100% 또는 알람 362 | 주의 | OPR, MNT |

### 6.4 안전 원칙 (기획서 2.1에서 그대로)

- 설비를 원격으로 조작하지 않는다.
- 정비가 필요한 알람의 카드·작업지시서에는 안전 고정 서식이 항상 붙는다.
- 카탈로그에 `safety_in_source`가 없는 행은 "원문에 안전 문단 없음"이라고 표시하지 않고, **A6 매트릭스가 정한 안전 요건**을 적용한다. (원문에 없다고 안전 절차를 생략하지 않는다)

## 7. 가상 데이터 생성기와의 연결

정비 데이터는 **카탈로그를 읽어서 만든다**. 이 연결이 설계서 5.9의 "원인·조치는 TSG에 적힌 것만" 원칙을 지키는 방법이다.

| 생성하는 것 | 카탈로그 사용 방식 |
|---|---|
| 정비 이력의 원인 | 알람별 카탈로그의 `cause_id` 중에서 선택 (`evidence_level`이 직접인 행에 높은 확률) |
| 정비 이력의 조치 | 선택한 행의 `action_ko`를 짧게 변형 |
| 교체 부품 | 원인에서 파생 (예: C-991-02 냉각 팬, C-993-04 파워 케이블) [부품 번호 쓰지 않음] |
| 작업자 메모 | 선택한 `cause_id`에서 대충 쓴 말투로 변환 (정답 `cause_id`를 함께 저장해 MNT-05 평가에 사용) |
| 알람 순서 | `108 → 994 → 992` 등 TSG의 충돌 신호 문장 |
| 반복 알람 | 2075 등이 30일에 여러 번 (설계서 5.9) |

**정합성 점검 항목 추가** [제안] (설계서 9장에 더하기)

| 점검 | 기준 |
|---|---|
| 이력의 `cause_id`가 해당 알람의 카탈로그에 존재 | 100% |
| 모든 정비 작업지시서에 안전 6+3단계 체크 | 100% |
| 승인자 역할이 MNT 또는 MGR | 100% |
| 상태 시각 순서(작성 < 승인 < 착수 < 완료) | 위반 0 |
| 이력의 수리 시간 = DOWN 구간 길이 | 오차 1분 이내 |
| 모든 PM 항목이 `pm_task`에 존재 | 100% |
| 시연용 연체 PM 항목 | 2~3개 |
| 같은 알람 반복 횟수 | S2용으로 2075가 30일에 3회 이상 |
